# 레시피: 개인정보 열람·정정·삭제·처리정지 요구 처리 `[대외]`

> 확정: 2026-10-19 | 테이블: `schemas/25_privacy_request.sql` | 원칙: personal-data.md(접속기록·마스킹), state-machine.md(조건부 전이) | 짝: account-withdrawal.md(삭제·분리 보관), consent.md(동의 철회), marketing-message.md(수신 거부), inquiry.md(접수 창구), batch.md(기한 감시)
> 정보주체의 요구는 **받은 날부터 달력일 10일** 안에 처리하고 결과를 알린다. 셀프서비스로 즉시 끝나는 것(내 정보 보기·수정·수신 거부·탈퇴)은 화면이 처리하고, 나머지는 **요청 테이블에 기한과 함께 접수**해 배치가 기한을 지킨다.

## 1. 언제 쓰나

개인정보를 처리하는 모든 서비스(대외 회원·비회원 고객). 사내 시스템의 임직원 정보도 법 적용 대상이지만 요구 건수가 적어 인사 부서 절차로 처리하는 경우가 많다 — 그때도 1-1절의 기한·통지는 같다.

### 1-1. 법정 요건 (원문 확인 2026-10-19 — legalize-kr: 법제처 데이터를 옮긴 공개 저장소)

법률은 2026-09-08 공포본(2027-03-09 시행)으로 확인했고, 아래 조문(제35~38조)은 그 개정의 대상이 아니다. 시행령은 2026-09-11 시행본, 표준 개인정보 보호지침은 2025-04-11 시행본.

| 항목 | 내용 | 근거 |

| 열람 기한 | 받은 날부터 **10일** 이내 열람하게 하거나, 연기·거절이면 10일 이내 **사유 + 이의제기방법** 통지. 연기 사유가 없어지면 그날부터 10일 이내 | 법 제35조 ③④, 시행령 제41조 ④⑤·제42조 ②, 표준지침 제31조 ① |

| 일부 제한 | 법률상 금지·제한, **다른 사람의 생명·신체·재산 등 이익을 부당하게 침해할 우려** 등 → 그 부분만 제한하고 나머지는 열람 | 법 제35조 ④, 시행령 제42조 ① |
| 정정·삭제 | 지체 없이 조사해 조치하고 10일 이내 결과 통지. **다른 법령이 수집 대상으로 명시한 정보는 삭제 요구 대상이 아니다** — 그 사실·이유·이의제기방법 통지. 삭제는 복구·재생되지 않게. 확인에 필요한 증거자료를 요구할 수 있다 | 법 제36조 ①~⑤, 시행령 제43조 ③, 표준지침 제32조 |
| 처리정지 | 10일 이내 정지(전부·일부) + 통지. 거절 사유: 법률 규정·법령상 의무 / 타인의 이익 침해 / **서비스 제공이 불가능한데 정보주체가 해지 의사를 밝히지 않은 경우** 등. 정지된 정보는 10일 이내 파기 등 조치 | 법 제37조 ②⑤, 시행령 제44조 ②, 표준지침 제33조 |
| 동의 철회 | 지체 없이 파기 등 조치, 하지 않으면(처리정지 거절 사유와 같은 경우) 사유 통지 | 법 제37조 ③④ |

| 수수료 | 실비 범위에서 처리자가 정한다. **요구 사유가 처리자에게 있으면 청구 금지** | 법 제38조 ③, 시행령 제47조 ①② |
| 이의제기 | 거절 등에 불복할 수 있는 절차를 마련하고 안내 | 법 제38조 ⑤ |
| 전송 요구 | **평균매출액 1,800억원 초과이면서 정보주체 100만 명 이상(민감·고유식별정보는 5만 명 이상)** 등 시행령 기준에 해당하는 처리자만 | 법 제35조의2, 시행령 제42조의2 ① |
| 기한 계산 | 초일 불산입, 말일의 종료로 만료, **말일이 토요일·공휴일이면 다음 날 만료** | 민법 제155·157·159·161조 (2026-03-17 시행본) |

- 기한·대상은 개정이 잦다 — 착수 시 현행 원문을 다시 확인해 CLAUDE.md에 기록한다 (MANDATORY).
- 통지서 양식은 보호위원회가 고시한다(시행령 제41조 ⑤ 등 "보호위원회가 정하여 고시하는 … 통지서") — 이 레시피는 고시 서식 원문을 확인하지 않았다. 통지 문구에 3-4절 항목을 빠짐없이 넣고, 서식은 법무가 확인한다.
- 자동화된 결정에 대한 거부·설명 요구(법 제37조의2)도 열람등요구에 포함된다 — 자동화된 결정을 하는 서비스만 해당하며 이 레시피 범위 밖.

## 2. 결정 항목 (기본값)

| 결정 | 기본값 | 대안 / 비고 |
|---|---|---|
| 셀프서비스 | **회원은 화면에서 즉시** — 내 정보 보기(열람), 정보 수정(정정), 수신 설정(동의 철회·처리정지 일부), 탈퇴(삭제) | 즉시 처리는 기한 문제가 없다 — 요청 테이블은 셀프서비스로 안 되는 것만 |
| 접수 창구 | 마이페이지 요청 폼 + 비회원 요청 폼 + 고객센터(전화·메일) → **모두 같은 요청 테이블** | 고객센터 수기 접수도 담당자가 같은 화면으로 등록 — 기한 감시에서 빠지지 않게 |
| 본인 확인 | 회원 = 로그인 / 비회원 = **수집할 때 받은 연락처로 인증**(이메일 OTP 등) / 대리인 = 위임장 + 대리인 본인 확인 | **신분증 사본 요구 금지** — 수집 때 받지 않은 증빙(표준지침 제34조) + 불필요한 고유식별정보 수집 |
| 기한 | `due_date` = 받은 날(한국 날짜) + 10일, 말일이 토·일·공휴일이면 다음 평일 — 접수 시 계산해 저장 | 공휴일은 공통코드 그룹 `HOLIDAY`(code = `YYYY-MM-DD`) — 해마다 등록 |
| 내부 목표 | 기한 **3일 전** 담당자 알림, 당일 미처리면 개인정보 보호책임자에게 | |
| 수수료 | **받지 않는다** | 받으려면 실비 범위 + 처리방침 공개 + 처리자 사유면 면제 |
| 열람 제공 형식 | 로그인한 본인 화면에 표시(비회원은 인증 후 1회 조회) — 파일은 본인 인증된 요청에서만 내려준다 | 메일 첨부 금지(전달·오발송), 우편 사본은 우송료 청구 가능 |
| 전송 요구 | **해당 없음**을 프로젝트 시작 시 확인 (1-1절 기준) | 해당하면 별도 설계 — 이 레시피 범위 밖 |

## 3. 표준 설계

### 3-1. 접수와 상태

```
접수:  INSERT privacy_request (public_id, user_id?, request_type, detail, identity_method, received_at, due_date = dueDate(...))
       → 접수 확인 메일(접수 번호 = public_id, 처리 기한) — outbox 경유
처리:  RECEIVED ─▶ IN_PROGRESS ─▶ DONE      (결과 통지)
                        │      └▶ REJECTED  (사유 + 이의제기방법 통지 — 일부 제한도 DONE + reason)
                        └▶ DEFERRED ─▶ IN_PROGRESS   (열람 연기만 — 사유 통지, 사유 소멸 시 due_date 재계산)
전이:  UPDATE privacy_request SET status = :to, version = version + 1, …
        WHERE privacy_request_id = :id AND status = :from AND version = :v      ← 0행이면 다른 담당자가 먼저 처리 (state-machine.md)
```

- 담당자 화면에서 요청을 여는 것 자체가 개인정보 조회다 — 접속기록 대상(personal-data.md).
- 비회원 요청은 인증을 마칠 때까지 `privacy_request` 행을 만들지 않는다(인증 안 된 요청으로 기한이 시작되지 않게 — 인증 메일 발송 기록만 남긴다). 인증 후 접수 시각이 `received_at`.

### 3-2. 기한 계산

```js
/**
 * 열람등요구 처리 기한 — 받은 날 다음 날부터 세어 days일째 날(초일 불산입, 민법 제157조).
 * 그날이 토·일·공휴일이면 다음 날로 넘긴다(민법 제161조). 영업일로 세지 않는다.
 * @param {string} receivedDate 받은 날 — 한국 날짜 YYYY-MM-DD (서버 시간대로 자르지 않는다)
 * @param {number} days 기한 일수 (시행령 제41조 ④ 등 — 10)
 * @param {Set<string>} holidays 공휴일 YYYY-MM-DD (공통코드 HOLIDAY)
 */
export function dueDate(receivedDate, days, holidays) {
  const d = new Date(`${receivedDate}T00:00:00Z`);                 // 날짜 계산만 — UTC 자정 기준이라 실행 환경 시간대 영향 없음
  d.setUTCDate(d.getUTCDate() + days);
  const iso = () => d.toISOString().slice(0, 10);
  while (d.getUTCDay() === 0 || d.getUTCDay() === 6 || holidays.has(iso())) d.setUTCDate(d.getUTCDate() + 1);
  return iso();
}

/** 받은 날 = 한국 날짜 — sv-SE 로캘이 YYYY-MM-DD 형식을 준다 */
export const kstDate = (at) => new Intl.DateTimeFormat('sv-SE', { timeZone: 'Asia/Seoul' }).format(at);
```

- 실측 2026-10-19 (Node 22, Java 21 `LocalDate.plusDays` + 같은 판정 — 결과 동일, 공휴일 10-03·10-05·10-09·12-25):

| 받은 날 | 기한 | 확인한 것 |
|---|---|---|
| 2026-10-19(월) | 10-29(목) | 기본 |
| 2026-10-21(수) | 11-02(월) | 말일 10-31(토) → 다음 평일 |
| 2026-09-29(화) | 10-12(월) | 말일 10-09(공휴일) → 주말 건너 월요일 |
| 2026-12-15(화) | 12-28(월) | 말일 12-25(공휴일) → 주말 건너 월요일 |

- 같은 실측에서 **영업일 10일로 세면 10-19 접수 → 11-02, 09-29 접수 → 10-15** — 법정 기한보다 4일·3일 늦다(4절).

### 3-3. 유형별 처리

| 유형 | 처리 | 남길 것 |
|---|---|---|
| ACCESS 열람 | 시행령 제41조 ① 다섯 항목 중 요구한 것: 항목·내용(user·주문 등 업무 테이블), 목적·보유기간(**동의한 처리방침 버전** — consent.md), 제3자 제공 현황(제공 대장·위탁사 목록), 동의 사실(`user_consent` 이력) | `result_summary`에 제공 범위, 제한한 부분은 `reason` |
| CORRECTION 정정 | 정정 → 변경 이력(change-history.md)에 "열람등요구 #public_id"를 사유로 | 바뀐 항목 |
| DELETION 삭제 | 항목 삭제 또는 탈퇴 처리(account-withdrawal.md 3-1절). **법정 보존 대상은 삭제하지 않고 분리 보관** — 그 사실·근거 법령·이의제기방법을 통지 | 삭제 항목, 보존한 항목과 근거 |
| SUSPENSION 처리정지 | 해당 처리(예: 맞춤 추천·마케팅)를 끄는 플래그 + 이미 처리된 정보 파기. 서비스 제공 자체가 불가능하면 거절 사유 4호 — **해지 의사를 물어** 해지하면 탈퇴로 | 정지한 처리, 거절이면 사유 |
| WITHDRAW_CONSENT 동의 철회 | consent.md — 철회 행 INSERT. 마케팅이면 marketing-message.md 수신 거부와 같은 경로 | 철회한 동의 |

- 위탁사(메일 발송 대행·CRM 등)에 사본이 있으면 그쪽에도 같은 조치를 요청하고 회신을 받아 `result_summary`에 남긴다.
- 백업에서 복원하면 처리한 정정·삭제를 다시 적용해야 한다 — account-withdrawal.md의 파기 목록과 같이 관리한다.

### 3-4. 통지와 기한 감시

- 통지에 넣을 것: 접수 번호·받은 날·처리 결과(열람이면 열람할 정보와 일시·방법) / 거절·연기·일부 제한이면 **사유 + 이의제기방법**(누구에게·어떻게) — 시행령 제41조 ⑤·제42조 ②·제43조 ③·제44조 ②.
- 통지는 outbox로 보내고, **`notified_at`이 기한 판정 기준**이다(완료 처리만 하고 알리지 않으면 기한 안에 처리한 것이 아니다).
- 기한 감시 배치(매일, batch.md 3절 실행 이력):

```sql
SELECT public_id, request_type, due_date, status
  FROM privacy_request
 WHERE status IN ('RECEIVED', 'IN_PROGRESS', 'DEFERRED')
   AND due_date <= CURDATE() + INTERVAL 3 DAY          -- DB 세션 시간대가 Asia/Seoul이어야 CURDATE()가 한국 날짜 (database.md)
 ORDER BY due_date;
```

## 4. 함정 (STRICT)

| 함정 | 증상 | 처방 |
|---|---|---|
| 영업일로 기한 계산 | 법정 기한보다 **3~4일 늦은 날짜**를 기한으로 관리 (실측: 10-19 접수 → 11-02, 법정 10-29) | 달력일 + 말일만 휴일 연장 (3-2절) |
| 서버 시간대 날짜로 "받은 날" 판정 | 한국 00:30 접수가 UTC 전날로 잘려 **통지서에 법정 기한과 다른 날짜** (실측: 10-29 vs 10-30) | 한국 날짜로 자른 뒤 계산 (`kstDate`) |
| 신분증 사본·추가 서류 요구 | 수집 때 요구하지 않은 증빙 — 표준지침 제34조 위반 + 불필요한 고유식별정보 수집 | 수집 때 받은 수단으로 본인 확인 |
| 요구 창구가 전화뿐(가입은 웹) | 수집 방법보다 어려운 절차 (시행령 제41조 ②) | 웹 폼 + 홈페이지 공개 |
| 거절·연기를 통지하지 않음 | 기한 경과 + 사유·이의제기방법 통지 의무 위반 | REJECTED·DEFERRED 전이에 통지 문구 필수(빈 `reason` 거부) |
| 삭제 요구에 전부 물리 삭제 | 법정 보존 거래기록까지 삭제 | 분리 보관 + 보존 사실 통지 (account-withdrawal.md) |
| 열람 결과에 다른 사람 정보 | 상담 메모·공동 배송지·다른 회원 이름이 그대로 나간다 | 그 부분만 제한하고 나머지 제공 (시행령 제42조 ①) |
| 고객센터 수기 접수를 메일함에만 | 기한 감시에서 빠진다 | 같은 요청 테이블에 등록 |
| 처리정지 후에도 발송 계속 | 대상 목록 작성 뒤 정지·철회한 사람에게 발송 | 발송 직전 확인 (marketing-message.md) |
| 비회원 요청 폼을 인증 없이 처리 | 남의 정보를 열람·삭제 | 수집한 연락처 인증 후 접수 |

## 5. 스택별 구현

| 구성 | Express | Spring |
|---|---|---|
| 기한 계산 | `dueDate` + `kstDate` (3-2절, 실측) | `received.plusDays(10)` + 토·일·공휴일이면 `plusDays(1)` 반복, 받은 날은 `LocalDate.ofInstant(at, ZoneId.of("Asia/Seoul"))` (실측 — Node와 같은 결과) |
| 상태 전이 | 조건부 UPDATE (state-machine.md) | 동일 |
| 기한 감시 | batch.md 1절 방식 중 프로젝트에서 정한 것 | `@Scheduled` + 실행 이력 |
| 화면 | 담당자 목록 = 기한 오름차순 + 남은 일수 강조, 요청 열람은 접속기록 | 동일(프론트) |

## 6. 검증 포인트

- 자동화 테스트: 3-2절 표의 네 날짜(평일·토요일 말일·공휴일 말일·연말 공휴일) + 한국 자정 직후 접수 / 같은 요청을 두 담당자가 동시에 완료 → 한쪽만 성공 / `reason` 없이 REJECTED 전이 → 거부.
- 수동: 비회원 요청 폼이 인증 전에 행을 만들지 않는지, 담당자 화면 열람이 접속기록에 남는지, 처리정지·동의 철회 직후 마케팅 발송 대상에서 빠지는지.
- 처리방침에 요구 방법·창구·이의제기 방법이 공개돼 있는지(시행령 제41조 ②3호).
