# 레시피: 개인정보 유출 대응 — 대상 산정·통지·신고 `[공통]`

> 확정: 2026-10-20 | 테이블: `schemas/26_privacy_breach.sql` | 원칙: personal-data.md(접속기록 — 대상 산정의 원천), ops.md 4절(장애 대응 기록) | 짝: field-encryption.md(암호화가 피해 범위를 줄인다), sms-message.md·mail-domain-auth.md(통지 발송), outbox.md, error-alert.md, gdpr.md 3-3절(해외 이용자)
> 개인정보가 분실·도난·유출·위조·변조·훼손("유출등")된 것을 **알게 된 때부터 72시간** 안에 정보주체에게 알리고, 신고 대상이면 같은 72시간 안에 보호위원회 또는 한국인터넷진흥원에 신고한다. **전부 확인될 때까지 기다리지 않는다** — 확인된 것으로 먼저 알리고, 더 확인되는 대로 다시 알린다. 대상자는 접속기록에서 **한 사람 한 행**으로 뽑아 센다.

## 1. 언제 쓰나

개인정보를 처리하는 모든 시스템(사내 임직원 정보 포함). 예: 관리자 계정 탈취 뒤 고객 조회, 메일·문자 오발송(다른 사람의 정보), 설정 실수로 파일·버킷 공개, 노트북 분실, 위탁사(발송 대행·CRM) 사고, 백업 파일 노출, 데이터 변조.

이 레시피는 **시스템이 미리 갖춰 둘 것**(대응 기록·대상 산정·기한 감시·통지 발송)과 **대응 순서**를 정한다. 유출 해당 여부·신고 면제·통지 문구의 법적 판단은 개인정보 보호책임자와 법무가 한다 — 시스템은 그 판단에 필요한 숫자를 빠르고 정확하게 내놓는 것이 목적이다.

### 1-1. 법정 요건 (원문 확인 2026-10-20 — legalize-kr: 법제처 데이터를 옮긴 공개 저장소)

법률은 2026-09-08 공포본(2027-03-09 시행)으로 확인했고, 제34조는 2026-03-10 개정분(공포 6개월 뒤 시행 — 부칙 제1조)이다. 시행령은 2026-09-11 시행본, 고시는 「개인정보의 안전성 확보조치 기준」 2026-07-01 시행본.

| 항목 | 내용 | 근거 |
|---|---|---|
| 유출등 | 분실·도난·유출·위조·변조·훼손 | 개인정보 보호법 제23조 ② |
| 정보주체 통지 | 알게 된 때 **서면등의 방법으로 72시간 이내** — 접속경로 차단·취약점 보완·회수 등 **긴급 조치가 필요하면** 또는 천재지변 등이면 그 사유가 해소된 뒤 즉시 | 법 제34조 ①, 시행령 제39조 ① |
| 서면등의 방법 | 서면·전자우편·팩스·전화·문자전송 또는 이에 상당하는 방법 | 시행령 제17조 ⑤ |
| 통지 항목 | ① 유출등이 된 **항목** ② **시점과 경위** ③ 피해를 줄이려고 **정보주체가 할 수 있는 방법** ④ 처리자의 **대응조치와 피해 구제절차** ⑤ 피해 신고를 받는 **담당부서·연락처** ⑥ 손해배상·법정손해배상 청구, 분쟁조정 등 **법적 권리와 행사 방법** ⑦ 대통령령으로 정하는 사항 | 법 제34조 ① 1~7호 |
| 일부만 확인됨 | 항목(1호)·시점·경위(2호)를 아직 모르면 **유출 사실·확인된 내용·3~6호를 먼저 통지**, 추가로 확인되는 즉시 다시 통지 | 시행령 제39조 ② |
| 연락처를 모름 | 홈페이지에 **30일 이상 게시**로 통지를 갈음(홈페이지가 없으면 사업장의 보기 쉬운 곳) | 시행령 제39조 ③ |
| **가능성 통지** | 불법 접근이 있었으나 정보주체를 특정하기 어렵거나, 일부 유출이 확인돼 다른 사람도 유출됐을 수 있으면 **가능성이 있는 모든 정보주체에게 72시간 이내** — 항목·시점·경위·3~5호·"확정되면 추가 통지" | 법 제34조 ②, 시행령 제39조의2·제39조의3 ① |
| 가능성 → 확정·해소 | 기한 안에 실제 유출이 확인되면 제34조 ① 통지로 갈음 / 유출되지 않은 것이 확인되면 **즉시 그 사실을 통지** | 시행령 제39조의3 ②③④ |
| 피해 최소화 | 회수·삭제 등 피해 확산 방지 조치 | 법 제34조 ③ |
| **신고** | 다음 중 하나면 **72시간 이내** 보호위원회 또는 **한국인터넷진흥원**에 신고: ① **1천명 이상** ② **민감정보·고유식별정보** ③ 개인정보처리시스템·업무용 기기에 대한 **외부의 불법 접근** | 법 제34조 ④, 시행령 제40조 ①③ |
| 신고 예외·분할 | 천재지변 등은 해소 후 즉시 / 경로를 확인해 회수·삭제 등으로 권익 침해 가능성이 **현저히 낮아지면** 신고하지 않을 수 있다 / 1·2호를 모르면 확인된 것으로 먼저 신고 후 추가 신고 | 시행령 제40조 ①② |
| 대응 계획 | 내부 관리계획에 **유출사고 대응 계획 수립·시행** 포함(1만 명 미만 소상공인 등은 생략 가능), 접속기록·다운로드 점검 | 「개인정보의 안전성 확보조치 기준」 제4조 ① 14호·제8조 ② |

- 기한·신고 기준은 개정이 잦다(2026년에만 법·시행령이 바뀌었다) — 착수 시 현행 원문을 다시 확인해 CLAUDE.md에 기록한다 (MANDATORY).
- 제34조 ① 7호의 "대통령령으로 정하는 사항"은 현행 시행령에서 별도 조항을 찾지 못했다 — 통지 문구는 1~6호로 쓰고 법무가 확인한다.
- 해외(EU) 이용자가 있으면 GDPR 기준을 더한다 — 기관 신고 대상이 더 넓다(위험 가능성이 낮지 않은 모든 유출, gdpr.md 3-3절 원문 비교표).

## 2. 결정 항목 (기본값)

| 결정 | 기본값 | 대안 / 비고 |
|---|---|---|
| 대응 책임자 | **개인정보 보호책임자** — 부재 시 대행자를 CLAUDE.md·내부 관리계획에 | 72시간은 주말·휴일에도 흐른다 — 연락 순서를 미리 |
| 기산점 | **처음 알게 된 시각**(`detected_at`) — 제보·알림·로그 이상을 처음 본 시각 | "확인을 마친 시각"부터 세지 않는다 (4절) |
| 기한 계산 | `deadline_at = detected_at + 72시간` — 저장 시 계산, **날짜로 자르지 않는다** | |
| 대상 산정 | 접속기록에서 `privacy_breach_subject`로 **한 사람 한 행** (3-2절) | 오발송·파일 공개는 발송 이력·파일 내용에서 같은 표로 |
| 신고 판정 | 1천명(대상 행 수 + 목록 없는 기록의 하한), 민감·고유식별정보 여부, 외부 불법 접근 여부 — **셋 중 하나라도면 신고** | 면제(시행령 제40조 ① 단서)는 법무 판단 + 사유 기록 |
| 통지 채널 | **이메일**(outbox, 대량 발송 속도 조절 — mail-domain-auth.md) + 이메일이 없거나 실패한 사람은 **문자**(sms-message.md) | 연락처가 없는 사람이 남으면 홈페이지 30일 게시 |
| 통지 문구 | 3-3절 틀(1~6호) — 보호책임자·법무 승인 후 발송, **보낸 문구 원문을 `privacy_breach_notice`에** | |
| 기한 감시 | 대응 행이 열려 있으면 **1시간마다** 남은 시간을 대응 채널로 (error-alert.md 경로) | |
| 증거 보존 | 조사 시작 전에 해당 기간의 접속기록·애플리케이션 로그·프록시 로그를 **별도 보관** — 보관 주기 삭제가 증거를 지우지 않게 | |

## 3. 표준 설계

### 3-1. 대응 순서

```
T+0   알게 됨 → privacy_breach INSERT (kind, breach_type, cause, detected_at, deadline_at = detected_at + 72h)
      → 보호책임자·대응 채널 호출, 기한 감시 시작
T+?   긴급 조치: 계정 잠금·세션 종료(session-control.md), 키·비밀 교체(ops.md 1절), 공개 설정 해제, 위탁사 차단
      → contained_at
      대상 산정(3-2절) → affected_count, has_sensitive, report_required
≤72h  정보주체 통지(우선 통지 seq=1) + 신고 대상이면 신고(seq=1)
      — 항목·경위가 덜 확인됐어도 이 시점에 보낸다 (시행령 제39조 ②·제40조 ②)
이후  추가 확인 → 추가 통지·신고(seq=2…) / 연락처 없는 대상 → 홈페이지 게시(posted_until ≥ 게시일 + 30일)
종료  CLOSED + incident 문서(ops.md 4절)에 타임라인·원인·재발 방지
```

- 72시간을 넘기면 `delay_reason`(긴급 조치·천재지변 등 시행령 단서의 사유)을 반드시 남긴다 — 빈 값이면 CLOSED로 전이하지 못하게 조건부 UPDATE에 `delay_reason IS NOT NULL OR notified_at <= deadline_at`을 건다.
- 가능성(POSSIBLE)으로 시작해 확인되면 `kind = 'CONFIRMED'`로 바꾸고 제34조 ① 통지를 한다. **기한은 처음 알게 된 때 그대로**(보수적 해석 — 다른 해석은 법무 판단). 유출이 아니었음이 확인되면 그 사실을 즉시 통지한다(시행령 제39조의3 ③).

### 3-2. 대상 산정 — 접속기록에서

```sql
-- 탈취된 계정이 기간 중 처리한 정보주체를 한 사람 한 행으로 — 다시 실행해도(범위 확대) 중복되지 않고 원문 노출 여부만 누적된다
INSERT INTO privacy_breach_subject (privacy_breach_id, subject_type, subject_id, raw_exposed, first_accessed_at)
SELECT * FROM (
  SELECT :breachId AS bid, l.subject_type, j.subject_id,
         MAX(l.action IN ('UNMASK', 'DOWNLOAD')) AS raw,           -- 원문이 나간 기록이 하나라도 있으면 1
         MIN(l.accessed_at) AS first_at
    FROM {DB_NAME}_log.personal_data_access_log l
    JOIN JSON_TABLE(l.subject_ids, '$[*]' COLUMNS (subject_id VARCHAR(64) PATH '$')) j
   WHERE l.user_id = :compromisedUserId
     AND l.accessed_at >= :from AND l.accessed_at < :to
   GROUP BY l.subject_type, j.subject_id
) s
ON DUPLICATE KEY UPDATE raw_exposed = GREATEST(privacy_breach_subject.raw_exposed, s.raw);

-- 목록 없이 건수만 남은 기록(1,000행 넘는 다운로드 — personal-data.md 3-3절)은 위 JOIN에서 빠진다 — 따로 센다
SELECT COUNT(*) AS rows_without_list, SUM(subject_count) AS subjects_lower_bound
  FROM {DB_NAME}_log.personal_data_access_log
 WHERE user_id = :compromisedUserId AND accessed_at >= :from AND accessed_at < :to AND subject_ids IS NULL;
```

- 목록 없는 다운로드가 있으면 그 다운로드의 **조회 조건으로 같은 추출을 다시 실행**해 대상을 확정한다(조건은 audit_log에 남아 있다 — excel-download.md 2절) — 그 전까지 신고 판정은 `대상 행 수 + 하한`으로 한다.
- 계정 탈취가 아니라 IP로 찾아야 하면 `WHERE ip_address = :ip`로, 여러 계정이면 `user_id IN (…)`로 바꾼다 — 대상 표는 같다.
- 실측 2026-10-20 (MariaDB 11.4.13 · MySQL 8.4.11 — 결과 동일, 위 SQL 그대로): 탈취 계정이 고객 목록 24쪽(쪽당 50명)을 **두 번씩** 열람 + 원문 열람 5건 + 목록 없는 3,000행 다운로드 1건 →

| 세는 방법 | 값 | 신고 판정(1천명) |
|---|---|---|
| 접속기록 행 수 | 54 | **신고 안 함 — 틀림** |
| `subject_count` 합계 | 5,405 | 신고(규모를 실제보다 크게 신고) |
| **대상 표 행 수**(중복 제거) | **1,200**(원문 노출 5) | 신고 |
| 목록 없는 기록 | 1행·3,000명 — JSON_TABLE에서 빠짐 | 하한으로 따로 더한다 |

- 좁은 기간으로 먼저 산정한 뒤 기간을 넓혀 다시 실행해도 대상 표는 1,200행 그대로였다(중복 없음).

### 3-3. 통지 문구 틀 (법 제34조 ① 1~6호)

```
제목: [회사명] 개인정보 유출 사실을 알려드립니다

1. 유출된 항목: {items — 원문이 나간 항목과 가려진 상태로 보인 항목을 나눠 적는다 / 확인 중이면 "확인 중 — 확인되는 즉시 다시 알려드립니다"}
2. 유출 시점과 경위: {occurred_from}~{occurred_to}, {summary}
3. 피해를 줄이기 위해 하실 수 있는 일: {비밀번호 변경 링크, 의심 연락·문자 주의, 결제 내역 확인 등 — 유출 항목에 맞게}
4. 회사의 조치와 피해 구제 절차: {긴급 조치 내용, 보상·구제 절차}
5. 피해 신고·문의: {담당 부서, 전화, 이메일}
6. 손해배상·분쟁조정 등 권리: {손해배상·법정손해배상 청구, 개인정보 분쟁조정위원회 분쟁조정 신청 방법}
```

- 통지에 **유출된 값 자체를 다시 적지 않는다** — 통지가 또 하나의 유출 경로가 된다. 항목명만.
- 대상 표의 `notified_at`이 비어 있는 사람에게만 보낸다 — outbox `message_key` = `breach:{public_id}:{seq}:{subject}`로 같은 통지가 두 번 가지 않는다(notification.md 3-1절).
- 발송이 끝나면 `privacy_breach_notice`에 실제 보낸 문구·대상 수를 남기고, 실패해 연락이 안 된 사람이 남으면 홈페이지 게시로 넘긴다.

## 4. 함정 (STRICT)

| 함정 | 증상 | 처방 |
|---|---|---|
| 전부 확인될 때까지 통지·신고 보류 | 조사에 며칠 걸리는 동안 72시간이 지난다 — 시행령은 확인된 것만으로 먼저 알리라고 정했다 | 우선 통지·신고 후 추가 (3-1절) |
| "확인을 마친 시각"을 기산점으로 | 실제 기한보다 늦게 잡힌다 | `detected_at` = 처음 알게 된 시각 |
| **접속기록 행 수로 대상 수를 셈** | 목록 한 화면에 수십 명이 한 행 — 1,200명을 54명으로 세어 **신고 대상을 놓친다** (실측) | 대상 표 행 수 (3-2절) |
| `subject_count` 합계로 셈 | 같은 사람을 여러 번 본 만큼 부풀린다 — 규모를 틀리게 신고 (실측: 1,200명 → 5,405) | 대상 표 행 수 |
| 목록 없는 대량 다운로드를 놓침 | JSON_TABLE에서 그 기록이 통째로 빠진다 (실측: 3,000명 누락) | 하한을 따로 세고 추출을 재실행 |
| 통지에 유출된 값을 다시 적음 | 통지 메일·문자가 새 유출 경로 | 항목명만 |
| 접속기록이 없거나 IP가 프록시 주소 | 대상을 특정하지 못해 **전체 회원**을 대상으로 통지해야 한다 | personal-data.md 3절(기록 범위)·rate-limit.md 3-1절(실제 IP)을 사고 전에 |
| 보관 주기 삭제가 조사 중에 돈다 | 조사 대상 기간의 로그가 지워진다 | 대응 시작 시 해당 기간 로그 별도 보관 (2절) |
| 위탁사 사고를 "우리 일 아님"으로 | 통지·신고 의무는 처리자(우리)에게 남는다 | 위탁 계약에 사고 즉시 통보 의무 + 위탁사 연락처를 대응 계획에 |
| 통지를 사람마다 두 번·누락 | 재실행·재시도로 중복, 실패자 누락 | `notified_at` + outbox 메시지 키 (3-3절) |
| 72시간 초과 사유를 안 남김 | 나중에 연기가 정당했는지 보일 수 없다 | `delay_reason` 없이 CLOSED 불가 (3-1절) |

## 5. 스택별 구현

| 구성 | Express | Spring |
|---|---|---|
| 대응 행 등록 | 관리자 화면(보호책임자 권한) → `privacy_breach` INSERT, 기한은 SQL `+ INTERVAL 72 HOUR` | 동일 (JdbcClient) |
| 대상 산정 | 3-2절 SQL — 앱 계정은 `{DB_NAME}_log`에 SELECT 권한이 있다(personal-data.md 3-4절) | 동일 |
| 기한 감시 | batch.md 1절 방식 — 1시간 주기, 열린 행의 남은 시간을 error-alert 경로로 | `@Scheduled(cron = "0 0 * * * *")` + 실행 이력 |
| 통지 발송 | 대상 표에서 `notified_at IS NULL` 묶음 → outbox(MAIL·SMS) → 발송 성공 시 `notified_at` | 동일 |
| 화면 | 대응 상세 = 남은 시간·대상 수·신고 판정 근거·통지 이력 | 동일(프론트) |

## 6. 검증 포인트

- 자동화 테스트(테스트 DB): 3-2절 시드 그대로 → 대상 1,200 · 원문 노출 5 · 목록 없는 기록 하한 3,000 / 기간을 넓혀 재실행 → 행 수 불변 / `delay_reason` 없이 기한 넘긴 행 CLOSED → 거부 / 같은 대상·차수 통지 두 번 → 한 번.
- 모의 훈련(연 1회 — 안전성 확보조치 기준 제4조 ④의 점검과 함께): 테스트 계정 탈취 시나리오로 알게 된 시각부터 우선 통지 문구 승인까지 걸린 시간을 재고, 72시간 안에 끝나는지와 대응 연락망이 휴일에도 닿는지 확인한다.
- 운영 전: 접속기록이 실제 IP·정보주체 ID를 남기는지(personal-data.md 6절), 통지 문구 틀을 법무가 확인했는지.
