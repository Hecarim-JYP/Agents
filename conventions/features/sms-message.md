# 레시피: 문자·알림톡 발송 연동 `[공통]`

> 확정: 2026-10-20 | 테이블: `schemas/07_outbox.sql`(`target_system` = `SMS`·`ALIMTALK`) | 원칙: outbox.md, notification.md 3-1절(사건 키) | 짝: account-lifecycle.md 3-4절(인증 코드), marketing-message.md(광고성), rate-limit.md(발송 빈도), webhook-receive.md(전달 결과)
> 문자는 **대행사에 미리 등록한 발신번호로만** 보낸다. 본문은 **CP949 바이트로 세어** SMS(90)·LMS(2,000)를 우리가 고르고, 표현할 수 없는 글자는 보내기 전에 막는다. 알림톡이 실패했을 때의 문자 대체 발송은 **대행사 한 곳에서만** 한다 — 우리가 또 보내면 두 통이 간다.

## 1. 언제 쓰나

인증 코드, 주문·배송·예약 안내, 장애 통지처럼 휴대폰으로 보내는 모든 메시지. 광고성 정보면 marketing-message.md 규칙(사전 동의·야간 제한·표기)이 추가로 붙는다. 앱 푸시는 이 레시피 범위 밖이다.

## 3. 표준 설계

### 3-1. 발송 흐름

```
안내·통지: 업무 트랜잭션 안에서 outbox INSERT (message_key = 사건 키 — notification.md 3-1절)
          → relay: 본문 렌더 → chooseType(3-2절) → 대행사 API (헤더 멱등 키 = message_key)
          → 접수 응답 = outbox SENT (전달 완료가 아니다) → 전달 결과는 대행사 결과 웹훅·조회로 따로 (webhook-receive.md)
인증 코드: 요청 처리 중 코드 발급(account-lifecycle.md 3-4절) → chooseType → 대행사 API 동기 호출(타임아웃 3초)
          → 실패·타임아웃이면 코드를 revoke하고 "다시 요청해 주세요" — 재시도 큐에 넣지 않는다
```

- 로그에는 **수신번호 마스킹(`010-****-1234`)과 메시지 유형·대행사 응답 코드만** 남긴다. 본문은 남기지 않는다 — 인증 코드·개인정보가 로그로 샌다 (ops.md 3절).
- 수신번호가 수신거부·광고 동의 철회 대상인지는 광고성일 때만 본다(marketing-message.md). 정보성 안내는 동의와 무관하게 보낸다.

### 3-2. 바이트 계산과 형식 결정

```js
import iconv from 'iconv-lite';

const SMS_MAX = 90;
const LMS_MAX = 2000;

/** 문자 본문 바이트 — CP949 기준(한글 2·ASCII 1). 대행사의 "EUC-KR 기준" 계산과 같은 값 (3-2절 실측) */
export const smsBytes = (text) => iconv.encode(text, 'cp949').length;

/** CP949로 표현할 수 없는 글자 — 인코딩하면 '?'로 바뀌어 원문과 달라지는 글자를 찾는다 */
export const unencodableChars = (text) =>
  [...text].filter((ch) => iconv.decode(iconv.encode(ch, 'cp949'), 'cp949') !== ch);

/**
 * 메시지 형식 결정 — 길이를 문자 수(length)나 UTF-8 바이트로 세지 않는다(4절)
 * @param {string} body 렌더가 끝난 본문
 * @returns {'SMS'|'LMS'}
 */
export function chooseType(body) {
  const bad = unencodableChars(body);
  if (bad.length > 0) throw new ValidationError(`문자로 보낼 수 없는 글자: ${bad.join(' ')}`);
  const bytes = smsBytes(body.replace(/\r\n/g, '\n'));     // CRLF는 2바이트 — 줄바꿈을 LF로 맞춘 뒤 센다
  if (bytes <= SMS_MAX) return 'SMS';
  if (bytes <= LMS_MAX) return 'LMS';
  throw new ValidationError(`문자 본문이 ${LMS_MAX}바이트를 넘는다: ${bytes}`);
}
```

- 변수(사용자 이름 등)는 템플릿에 넣기 **전에** `unencodableChars`로 걸러 빼고, 고정 문구는 템플릿마다 테스트에서 `chooseType`을 통과하는지 확인한다.
- 실측 2026-10-20 (Node 24.22 + iconv-lite 0.7.3, Java 21 `String.getBytes` / `CharsetEncoder.canEncode`):

| 본문 | `length` | UTF-8 | CP949 (Node `cp949`·Java `MS949`) | 판정 |
|---|---|---|---|---|
| 한글 45자 | 45 | 135 | 90 | SMS |
| 한글 46자 | 46 | 138 | 92 | LMS |
| 한글 90자 | 90 | 270 | 180 | LMS — `length <= 90`이면 SMS로 잘못 고른다 |
| 인증 코드 문구 44자(`[회사명] 인증번호 [123456]를 …`) | 44 | 94 | 69 | SMS — UTF-8로 세면 LMS로 잘못 고른다 |
| `똠`·`뷁`(KS X 1001 2,350자 밖 한글) | 1 | 3 | 2 | Node `euc-kr`도 2바이트(`8c63` — iconv-lite의 `euc-kr`은 CP949), **Java `EUC-KR`은 `?` 1바이트**(`canEncode` false) |
| `😀` · `₩`(U+20A9) · `–`(U+2013) | 2·1·1 | 4·3·3 | `?` 1바이트 | 표현 불가 — 두 스택 모두 `?`로 바뀐다 |
| `￦`(U+FFE6 전각) · `·` | 1 | 3·2 | 2 | 표현 가능 |
| `안녕\r\n하세요` | 7 | 17 | 12 (`\n`이면 11) | CRLF는 1바이트 더 |

- 대행사가 "EUC-KR"이라고 적어도 실제로는 CP949를 받는 경우가 많다 — `똠`이 포함된 이름이 실제로 제대로 가는지는 **연동 시 실발송으로 확인**해 CLAUDE.md에 기록한다. 확인 전에는 2,350자 밖 한글을 `?`로 바꾸지 말고 그대로 보낸다(Java에서 `EUC-KR`로 세면 그 글자가 이미 `?`가 된다 — 4절).

### 3-3. 알림톡 + 문자 대체 발송

```
outbox 1건(message_key) → 대행사 알림톡 API 한 번 호출: 템플릿 코드 + 변수 + 대체 발송 사용 + 발신번호(SMS_SENDER) + 대체 문구(chooseType 통과)
                       → 알림톡 실패(카카오톡 미사용·차단 등)면 대행사가 문자로 보낸다
                       → 결과 웹훅·조회: 최종 채널(ALIMTALK / SMS / LMS)과 성공 여부를 outbox 결과에 기록
```

- **대체 발송은 대행사 기능 한 곳에서만** — 우리 relay가 "알림톡 실패 → 문자 재발송"을 또 하면 대행사 대체 발송과 겹쳐 두 통이 간다. 대행사 대체 발송을 쓰지 않기로 했다면 반대로 우리 relay만 한다 (어느 쪽인지 CLAUDE.md에).
- 알림톡 템플릿은 검수받은 문구와 **글자 하나까지 같아야** 한다 — 템플릿 코드와 문구를 같은 모듈에 두고(notification.md 2절 "문구 템플릿 위치 = 코드"), 검수 반려·변경 이력을 남긴다.
- 정보성 템플릿에 쿠폰·이벤트 안내를 섞지 않는다 — 광고로 분류된다(marketing-message.md 1절, 업계 안내 — 2차 출처).

### 3-4. 발신번호 관리 (운영 절차)

| 시점 | 할 일 |
|---|---|
| 시작 | 대표번호를 대행사에 등록(통신서비스 이용증명원 등 대행사가 요구하는 서류) → `SMS_SENDER`에 같은 값 → 개발·운영 각각 실발송 1건 확인 |
| 번호 변경·회선 해지 | **새 번호 등록 → 설정 교체 → 실발송 확인 → 옛 번호 해지** 순서. 해지를 먼저 하면 그날부터 계정 발송이 막힌다(고시 제7조 ④) |
| 대행사 계정 담당자 교체 | 가입 본인 확인에 쓴 번호가 담당자 휴대폰이면 퇴사 후 해지될 때 계정이 막힌다 — 회사 번호로 바꿔 둔다 |
| 정기 | 운영 체크리스트에 "발신번호·대행사 계정 본인확인 번호 회선 유지" 항목 (ops.md) |

## 4. 함정 (STRICT)

| 함정 | 증상 | 처방 |
|---|---|---|
| `length`로 90자 판정 | 한글 90자 = 180바이트 → 잘려서 가거나 대행사가 LMS로 바꿔 요금이 바뀐다 (실측) | CP949 바이트 (3-2절) |
| UTF-8 바이트로 판정 | 한글 30자 남짓부터 LMS로 — 짧은 인증 문구도 LMS 요금 (실측: 44자 문구 94바이트) | CP949 바이트 |
| **Java `getBytes("EUC-KR")`로 계산·변환** | `똠`·`뷁` 같은 확장 한글이 **`?` 한 글자로 바뀌어** 이름이 깨지고 바이트도 틀린다 — Node `iconv-lite`의 `euc-kr`은 실제로 CP949라 같은 코드가 Node에서는 멀쩡하다 (실측: 스택마다 다른 결과) | 두 스택 모두 CP949 — Java `Charset.forName("MS949")` |
| 이모지·`₩`·`–`를 그대로 | `?`로 바뀌거나 대행사가 발송 실패 처리 (실측: 두 스택 모두 `?`) | `unencodableChars`로 발송 전에 막기 |
| 알림톡 실패 시 우리도 문자 재발송 | 대행사 대체 발송과 겹쳐 **같은 안내가 두 통** | 대체 발송은 한 곳에서만 (3-3절) |
| 발신번호 회선을 먼저 해지 | 그 계정의 **모든 발송이 막힌다** — 인증 코드가 안 가서 가입·로그인 전체가 멈춘다 (고시 제7조 ④) | 3-4절 순서 |
| 담당자 개인 번호로 발신·대행사 가입 | 퇴사·번호 해지와 함께 발송 중단 | 회사 대표번호 |
| 등록하지 않은 번호를 발신번호로 | 대행사가 거부 — 개발에서 쓰던 번호를 운영에 그대로 두면 운영 첫 발송부터 실패 | 환경별 `SMS_SENDER` + 운영 실발송 확인 (3-4절) |
| 인증 코드를 outbox 재시도로 | 5분짜리 코드가 재시도 끝에 늦게 도착 — 사용자는 이미 새 코드를 요청했다 | 동기 호출 + 실패 시 재요청 안내 (2절) |
| 접수 응답을 전달 완료로 기록 | 실제로는 결번·수신 차단으로 안 갔는데 "발송 완료" | 전달 결과는 결과 웹훅·조회로 따로 (3-1절) |
| 본문·수신번호 원문을 로그에 | 인증 코드·개인정보가 로그에 남는다 | 번호 마스킹, 본문 미기록 (3-1절) |
| 발송 API를 빈도 제한 없이 | 남이 우리 비용으로 문자를 보낸다 | 대상·IP 빈도 제한 + 하루 상한 (2절) |

## 5. 스택별 구현

| 구성 | Express | Spring |
|---|---|---|
| 바이트 계산 | `iconv-lite` `encode(text, 'cp949').length` (3-2절) | `text.getBytes(Charset.forName("MS949")).length` — `MS949` = `x-windows-949` |
| 표현 가능 검사 | `unencodableChars` (왕복 비교) | `Charset.forName("MS949").newEncoder().canEncode(ch)` 글자별 (`CharsetEncoder`는 스레드 안전하지 않다 — 호출마다 `newEncoder()`) |
| 대행사 클라이언트 | `external/sms` 모듈 하나(integration.md) — 타임아웃·멱등 키 헤더 | `RestClient` + 타임아웃 (integration.md) |
| 발송 | 안내 = outbox relay, 인증 코드 = 서비스에서 동기 호출 | 동일 |
| 전달 결과 | 결과 웹훅 수신(webhook-receive.md) 또는 relay가 주기 조회 | 동일 |

## 6. 검증 포인트

- 자동화 테스트: 3-2절 표의 경계(45·46자, 90자, 44자 인증 문구) / 이모지·`₩`·`–` → 발송 거부 / CRLF 본문의 바이트 / 템플릿마다 샘플 변수로 `chooseType` 통과 / 알림톡 실패 응답을 흉내 내도 우리 relay가 문자를 따로 보내지 않는다.
- 실발송(개발 계정): 등록 발신번호로 SMS·LMS 각 1건, 이름에 `똠`이 든 문자 1건(대행사 처리 확인 → CLAUDE.md 기록), 알림톡 미사용 번호로 대체 발송 1통만 오는지.
- 운영 전: 운영 `SMS_SENDER`가 운영 대행사 계정에 등록됐는지 실발송으로 확인, 하루 상한 알림이 error-alert로 오는지.
