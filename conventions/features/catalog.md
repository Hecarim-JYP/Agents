# 운영 기능 카탈로그 — 웹앱이 반드시 부딪히는 기능들의 표준 설계

> 신설: 2026-10-14 | 이 파일은 **인덱스**다 — 내용의 단일 출처는 각 레시피와 컨벤션 절이다. 여기에 내용을 요약하지 않는다.

옵저버(도메인 이벤트), outbox, 중복 제출 방지처럼 **운영하는 웹앱이라면 기능과 무관하게 반복해서 만드는 것들**을 미리 설계해 둔 목록이다. 패턴 이름보다 "언제 쓰고, 무엇을 정해야 하고, 어디서 사고가 나는가"를 정해두는 것이 목적이다.

## 1. 사용법 (MANDATORY)

- 아래 목록에 있는 기능을 구현할 때는 **코드를 쓰기 전에 해당 레시피 또는 컨벤션 절을 먼저 읽는다** — 레시피가 있는 기능을 즉흥 설계하지 않는다 (근거: 같은 기능을 프로젝트마다 다르게 만들면 같은 함정을 매번 다시 밟는다 — 실제로 이 카탈로그의 함정 대부분은 "모르면 운영에서만 터지는" 유형이다).
- 레시피의 "결정 항목"은 기본값이 있다. 기본값과 다르게 가면 이유와 함께 프로젝트 CLAUDE.md에 기록한다.
- 목록에 없는 반복 기능을 만들게 되면, 만든 뒤 레시피 후보로 이 표에 `☐`로 추가한다 (발견 즉시 기록).
- 레시피를 추가할 때 고칠 곳은 **레시피 파일 + 이 표 한 줄**이다. 스키마가 있으면 OVERVIEW 4-6절 표와 scaffolds/default.md 포함 조건, 시작 시 정할 결정이면 시작 결정 체크리스트를 함께 고친다. 다른 문서(dev-rules·README)에는 레시피 이름을 나열하지 않는다.

## 2. 레시피 형식

모든 레시피는 같은 6개 절로 쓴다 — 1. 언제 쓰나 / 2. 결정 항목(기본값) / 3. 표준 설계 / 4. 함정(STRICT — 증상·처방·근거) / 5. 스택별 구현(Express·Spring) / 6. 검증 포인트(자동화 테스트·/live-test). 함정의 근거는 **실측**(버전·날짜 명시) 또는 **원문 소스 확인**으로 남긴다.

## 3. 목록

태그: `[공통]` 모든 웹앱 / `[사내]` 업무 시스템 / `[대외]` 공개 서비스 — 대외 프로젝트는 `[공통]`+`[대외]`, 사내는 `[공통]`+`[사내]`를 검토한다.
상태: 📄 레시피 있음 / ✅ 기존 컨벤션이 다룸 / ◐ 일부만 다룸(레시피 예정) / ☐ 없음(레시피 예정). ⚑ = 되돌리기 어려운 결정 — 시작 결정 체크리스트(scaffolds/default.md) 후보.

- 5차(2026-10-20)도 같은 방식이다 — 개인정보 보호법·시행령, 정보통신망법, 민법, 전기통신사업법과 과기정통부 고시(발신번호 사전등록)를 원문으로 확인했고, 대행사 API 한도·알림톡 정책·CI/DI 정의는 2차 출처로 표시했다. 같은 차수에 기존 레시피의 Spring·인프라 "미검증" 표시 18건을 모두 실측으로 바꿨다.
- 6차(2026-10-20)는 사내 업무에서 반복되는 계산·출력 기능이다 — 부가가치세법, 공휴일에 관한 법률·관공서의 공휴일에 관한 규정(2026년 노동절·제헌절 추가), 근로기준법 원문을 확인했다. 별표 6·GDPR 원문은 네트워크 허용 후 2026-10-21에 확인했다.
