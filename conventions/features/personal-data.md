# 레시피: 개인정보 화면 마스킹·접속기록 `[사내]`

> 확정: 2026-10-14 | 테이블: `schemas/14_personal_data_access_log.sql` | 짝: excel-download.md, ops.md 3절(로그 마스킹), account-withdrawal.md(탈퇴·파기·분리 보관)
> 개인정보는 **서버가 가려서** 내보내고, 원문은 권한과 사유가 있을 때 한 건씩만 보여준다. 누가·언제·어디서·누구의·무엇을 처리했는지 **고칠 수 없는 접속기록**으로 남긴다.

## 1. 언제 쓰나

고객·임직원·거래처 담당자의 개인정보(이름+연락처, 주소, 고유식별정보, 민감정보)를 화면·엑셀로 다루는 시스템. 사내 업무 시스템도 개인정보처리시스템이다 — 대상이 임직원이어도 마찬가지다.

### 1-1. 법정 요건 (확인 범위를 명시한다)

| 항목 | 내용 | 확인 상태 |
|---|---|---|
| 접속기록 보관 | **1년 이상**. 정보주체 5만 명 이상 / 고유식별정보·민감정보 처리 / 기간통신사업자는 **2년 이상** (개인정보보호위원회 고시 「개인정보의 안전성 확보조치 기준」 제8조 제1항) | 2026-10-14 검색으로 두 출처 일치 확인 — **법제처 원문은 이 작업 환경에서 열람하지 못했다** |
| 점검·다운로드 확인 | 접속기록 점검과 개인정보 다운로드 확인의 주기·방법을 내부 관리계획으로 정해 이행 (제8조 제2항 — 이전 판본은 "월 1회 이상 점검") | 현행 문언 **미확인** — 프로젝트 착수 시 원문 대조 후 CLAUDE.md에 기록 |
| 기록 대상 업무 | 조회·등록·수정·삭제·다운로드·출력 등 개인정보를 처리한 업무 (실무 해설 기준) | 해설 자료 기준 |

⚠ 법령은 개정이 잦다. 기간·주기는 **착수할 때 원문을 다시 확인**하고, 확인 날짜와 함께 프로젝트 CLAUDE.md에 기록한다.

## 2. 결정 항목 (기본값)

| 결정 | 기본값 | 근거 |
|---|---|---|
| 개인정보 항목 목록 | 테이블·컬럼별로 **일반 / 고유식별 / 민감** 분류를 CLAUDE.md에 기록 | 무엇을 가리고 기록할지의 기준 |
| 마스킹 위치 | **서버**(응답을 만들 때) | 클라이언트에서 가리면 응답에는 원문이 실려 나간다 |
| 원문 열람 | 권한 코드 `personal.unmask` + **사유 입력** + 한 건·한 항목씩 | 목록 전체 원문 노출 차단 |
| 접속기록 보관 | **2년** (1-1절의 두 기준을 모두 만족) | |
| 접속기록 저장 위치 | **별도 DB**(`{DB_NAME}_log`) + 앱 계정은 **SELECT·INSERT만** | 3-4절 — 같은 DB에 두면 권한으로 막을 수 없다(실측) |
| 기록 실패 시 | **요청 실패**(개인정보 응답을 내보내지 않는다) | 기록 없는 개인정보 처리를 만들지 않는다 |

## 3. 표준 설계

### 3-1. 마스킹 — 형식이 맞지 않으면 통째로 가린다

```js
/*
 * 파일명 : personalMask.js
 * 용도 : 개인정보 화면 마스킹 — 서버가 응답을 만들 때 적용한다
 * 최초등록 : YYYY-MM-DD [박진영]
 */
const HIDDEN = '***';   // 형식을 알아볼 수 없는 값은 통째로 가린다 — 정규식이 안 맞아 원문이 나가는 것을 막는다

export const mask = {
  /** 이름: 첫·끝 글자 외 가림 — 홍길동→홍*동, 남궁민수→남**수, 홍길→홍* */
  name: (v) => {
    if (!v) return v;
    const c = [...String(v).trim()];                       // 문자 단위(한글·이모지 안전)
    if (c.length <= 1) return HIDDEN;
    return c.length === 2 ? c[0] + '*' : c[0] + '*'.repeat(c.length - 2) + c.at(-1);
  },
  /** 전화: 가운데 자리 가림 — 010-1234-5678·01012345678·010 1234 5678→010-****-5678 */
  phone: (v) => {
    if (!v) return v;
    const m = String(v).replace(/[\s-]/g, '').match(/^(\d{2,3})(\d{3,4})(\d{4})$/);
    return m ? `${m[1]}-${'*'.repeat(m[2].length)}-${m[3]}` : HIDDEN;
  },
  /** 이메일: 아이디 앞 2글자만 — hong.gd@corp.com→ho*****@corp.com */
  email: (v) => {
    if (!v) return v;
    const m = String(v).match(/^([^@\s]{1,2})([^@\s]*)@([^@\s]+)$/);
    return m ? `${m[1]}${'*'.repeat(m[2].length)}@${m[3]}` : HIDDEN;
  },
  /** 주민등록번호: 생년월일·성별 자리만 — 900101-1234567→900101-1****** */
  rrn: (v) => {
    if (!v) return v;
    const m = String(v).replace(/[\s-]/g, '').match(/^(\d{6})(\d)\d{6}$/);
    return m ? `${m[1]}-${m[2]}******` : HIDDEN;
  },
};
```

실측(2026-10-14): 위 예시 전부 기대대로 / `+82-10-1234-5678`·공백 섞인 이메일 → `***`. **처음 버전(형식 불일치 시 원문 반환)은 `잘못된값`을 그대로 내보냈다** — 그래서 통째로 가리는 쪽을 기본으로 한다.

- 목록·상세 응답 DTO를 만들 때 항목 분류(2절)에 따라 적용한다. 엑셀 다운로드도 같은 함수 (excel-download.md 3-1절).
- 개인정보가 담긴 응답에는 `Cache-Control: no-store` — 공용 PC의 브라우저 디스크 캐시에 남지 않게.

### 3-2. 원문 열람

- `POST /customers/:id/unmask` `{ field: 'phone', reason: '배송 문의 회신' }` → 권한 확인 → 접속기록(`UNMASK`, 항목·사유) → 그 한 값만 응답.
- 사유는 필수, 공백·한 글자 같은 무의미한 입력은 검증으로 거른다.

### 3-3. 접속기록 — 응답 전에

| 처리 | `action` | `subject_ids` |
|---|---|---|
| 목록 조회 | `VIEW` | 그 화면에 나간 행들의 정보주체 ID (페이지 크기 이내 — api.md 3절 상한) |
| 상세 조회 | `VIEW` | 1건 |
| 원문 열람 | `UNMASK` | 1건 + `fields`·`reason` |
| 엑셀 다운로드 | `DOWNLOAD` | 추출 행의 ID(최대 1,000개까지 목록, 그 이상은 `subject_count`만) + 사유 |
| 등록·수정·삭제 | `CREATE`·`UPDATE`·`DELETE` | 1건 |

- IP는 **프록시 뒤 실제 클라이언트 IP** — Express `app.set('trust proxy', 1)` / Spring `server.forward-headers-strategy` (docker.md 7절). 설정이 없으면 모든 기록의 IP가 프록시 주소가 된다. 프록시가 `X-Forwarded-For`를 덮어써야 위조 IP가 기록되지 않는다 (rate-limit.md 3-1절).
- 개인정보를 담은 응답을 **보내기 전에** 기록하고, 기록이 실패하면 500으로 끝낸다(2절).

### 3-4. 위·변조 방지 — 별도 DB + 권한

```sql
-- DBA(관리 계정)가 1회 실행 — 앱 계정은 접속기록을 쓰고 읽을 수만 있다
CREATE DATABASE {DB_NAME}_log CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
-- schemas/14_personal_data_access_log.sql 을 {DB_NAME}_log 에 생성
GRANT SELECT, INSERT ON {DB_NAME}_log.* TO '{DB_USER}'@'%';
```

- ⚠ **같은 DB에 두고 이 테이블만 권한을 빼는 것은 안 된다**: 앱 계정이 DB 단위 권한(`ON {DB_NAME}.*`)을 가지면 테이블 단위 REVOKE가 **ERROR 1147로 거부된다**(실측 2026-10-14, MariaDB 10.11). 스캐폴드 compose의 `MARIADB_USER`가 바로 DB 단위 전체 권한이다. 테이블 단위로만 권한을 주는 방식은 새 테이블마다 GRANT가 필요해 운영이 깨지기 쉽다 → **별도 DB**가 기본.
- 실측: 테이블 단위 SELECT·INSERT만 준 계정 → INSERT·SELECT 성공, UPDATE·DELETE는 ERROR 1142로 거부.
- 보관 기간이 지난 행의 삭제와 이 DB의 DDL은 **관리 계정으로만** 한다 (앱 마이그레이션 러너는 이 DB에 권한이 없다).

### 3-5. 점검

내부 관리계획의 주기로 아래를 확인하고 결과를 남긴다 (주기는 1-1절 원문 확인 후 확정):

- 업무시간 외 조회·다운로드 / 계정별 조회 건수 상위 / 대량 다운로드 / 사유가 비었거나 무의미한 원문 열람·다운로드.

## 4. 함정 (STRICT)

| 함정 | 증상 | 처방 |
|---|---|---|
| 화면(클라이언트)에서만 마스킹 | 응답 JSON에 원문 — 개발자 도구로 그대로 보인다 | 서버 마스킹 |
| 형식 불일치 시 원문 반환 | `+82-…`·공백 섞인 값이 **그대로 노출** (실측) | 통째로 가림 (3-1절) |
| 같은 DB에서 테이블 권한 회수 | ERROR 1147로 실패 → 결국 앱이 기록을 고칠 수 있는 상태로 운영 (실측) | 별도 DB (3-4절) |
| 프록시 뒤 IP 미설정 | 모든 기록의 접속지가 프록시 IP | trust proxy |
| 상세만 기록하고 목록은 생략 | 목록 화면으로 대량 열람해도 기록이 없다 | 목록도 `VIEW` |
| 엑셀 다운로드에 마스킹·기록 누락 | 화면에서 가린 값이 파일로 대량 유출 | excel-download.md와 같은 함수·`DOWNLOAD` 기록 |
| 로그·에러 알림에 개인정보 | 로그 파일·메신저로 퍼진다 | ops.md 3절, error-alert.md 3-2절 |
| 법정 기간·주기를 기억으로 적음 | 개정 후 기준 미달 | 1-1절 — 원문 확인 날짜와 함께 기록 |

## 5. 스택별 구현

| 구성 | Express | Spring |
|---|---|---|
| 마스킹 | 3-1절 모듈을 응답 DTO 매핑에서 | 응답 DTO 생성 시 같은 규칙의 유틸 (또는 Jackson 커스텀 Serializer — 권한별 분기가 어려우니 DTO 매핑 권장) |
| 접속기록 | 서비스에서 응답 직전 INSERT (`{DB_NAME}_log` 전용 커넥션 풀) | 같은 구조 — 별도 DataSource |
| 실제 IP | `app.set('trust proxy', 1)` + `req.ip` | `server.forward-headers-strategy: native` |
| 원문 열람 권한 | `requirePermission('personal.unmask')` | `@PreAuthorize` 또는 권한 인터셉터 |

## 6. 검증 포인트

- 자동화 테스트: 목록·상세 응답에 원문이 없다 / 형식 이상 값 → `***` / 권한 없는 원문 열람 → 403 / 원문 열람·다운로드 → 접속기록 1행(사유 포함) / 기록 INSERT 실패 → 응답 500.
- 실동작 검증(/live-test DB 축): 화면 조작 후 `{DB_NAME}_log`에 계정·실제 IP·정보주체 ID가 남는지, 앱 계정으로 접속기록 UPDATE를 시도하면 거부되는지.
