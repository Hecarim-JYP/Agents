# 레시피: 한글 검색 — 부분 일치·전문 검색 선택 `[공통]` ⚑

> 확정: 2026-10-20 | 원칙: sql.md(파라미터 바인딩), api.md 3절(목록·페이지 상한), database.md 1절(MariaDB 기본) | 짝: excel-download.md(같은 검색 조건 파서)
> 한글 검색의 기본은 **`LIKE '%검색어%'` + 이스케이프(`ESCAPE '!'`) + NFC 정규화 + 범위 조건 + 페이지 상한**이다. InnoDB **FULLTEXT 기본 파서는 한글에 쓰지 않는다** — 2글자 단어("크림")를 찾지 못한다. ngram 파서는 MariaDB에 없다. 수백만 행에서 드문 단어를 범위 조건 없이 찾아야 하면 검색 전용 저장소를 결정한다(⚑).

## 1. 언제 쓰나

목록 화면의 검색창(제품명·거래처명·문서 제목·고객명), 자동완성, 관리자 통합 검색. 정확 일치(코드·사업자번호·주문번호)는 이 레시피가 아니다 — 일반 인덱스 `=` 조회.

⚑ 되돌리기 어려운 이유: 검색 전용 저장소(별도 엔진)를 도입하면 색인 동기화(변경 → 재색인)·권한 필터·장애 대응이 함께 붙는다. 처음엔 DB로 시작하고, 3-3절 기준에 닿을 때 결정한다.

## 2. 결정 항목 (기본값)

| 결정 | 기본값 | 대안 / 비고 |
|---|---|---|
| 방식 | **`LIKE CONCAT('%', ?, '%') ESCAPE '!'`** | 앞부분 일치(`LIKE ?%`)만으로 충분한 화면(코드·이름 자동완성)은 일반 인덱스 range 조회 |
| 입력 처리 | 앞뒤 공백 제거 → **NFC 정규화** → `!`·`%`·`_` 앞에 `!` → **2자 미만 거부** | 1자 검색이 꼭 필요하면 범위 조건 필수 |
| 범위 조건 | 검색어와 함께 **기간·상태·법인(데이터 스코프)** 중 하나 이상을 기본값으로 건다(예: 최근 1년) | 전체 기간 검색은 사용자가 명시적으로 고를 때만 |
| 페이지 | api.md 3절 상한 + 키셋 또는 offset | |
| 전체 건수 | **상한 COUNT** — `SELECT COUNT(*) FROM (… LIMIT 1001) t` → 1,000건 넘으면 "1,000건 이상" | 정확한 건수가 업무상 필요하면 범위 조건을 좁혀서 |
| FULLTEXT | **쓰지 않는다** (한글) | 영문·숫자 위주 문서 검색이면 검토 |
| 검색 전용 저장소 ⚑ | 3-3절 기준에 닿으면 결정 — 형태소 분석·오타 허용·가중치가 필요할 때도 | 도입 시 색인 동기화는 outbox(outbox.md)로 |

## 3. 표준 설계

### 3-1. 검색어 처리와 쿼리

```js
/**
 * 검색어 → LIKE 패턴 인자 — 정규화·이스케이프·길이 검사를 한곳에서 (목록·엑셀 다운로드가 같은 함수를 쓴다)
 * @param {string} raw 사용자 입력
 * @returns {string} LIKE CONCAT('%', ?, '%') ESCAPE '!'에 바인딩할 값
 */
export function toLikeTerm(raw) {
  const term = String(raw ?? '').trim().normalize('NFC');           // macOS 등에서 온 NFD(자모 분리) 입력을 완성형으로
  if ([...term].length < 2) throw new ValidationError('검색어는 2자 이상 입력해 주세요');
  return term.replace(/[!%_]/g, (c) => `!${c}`);                    // 와일드카드를 글자로 — 이스케이프 문자는 '!'
}
```

```sql
-- 저장소: 검색어는 반드시 바인딩, 범위 조건과 함께
SELECT product_id, name, …
  FROM product
 WHERE company_id = :companyId                                -- 데이터 스코프 (auth.md 4-2절)
   AND created_at >= :from                                    -- 범위 조건 기본값
   AND name LIKE CONCAT('%', :term, '%') ESCAPE '!'
 ORDER BY product_id DESC
 LIMIT :size;

-- 전체 건수: 상한까지만 센다
SELECT COUNT(*) AS n FROM (SELECT 1 FROM product WHERE … AND name LIKE CONCAT('%', :term, '%') ESCAPE '!' LIMIT 1001) t;
```

- **이스케이프 문자를 `!`로 명시한다** — 백슬래시 이스케이프는 서버 `sql_mode`에 `NO_BACKSLASH_ESCAPES`가 있으면 조용히 틀린다(4절 실측).
- 저장할 때도 NFC로 정규화해 넣는다(입력 폼·엑셀 업로드 공통) — 검색어만 바꾸면 이미 NFD로 저장된 값이 안 찾아진다.

### 3-2. 실측 — 20만 행 (2026-10-20, MariaDB 11.4.13 · MySQL 8.4.11 — 별도 표시 없으면 두 DB 같은 결과)

제품명 20만 개, 절반은 띄어 쓰고(`수분 크림`) 절반은 붙여 썼다(`수분크림`). `innodb_ft_min_token_size` 기본값 3(두 DB).

| 검색 | 결과 | 시간 |
|---|---|---|
| `LIKE '%크림%'` | 50,048건 (정답) — EXPLAIN `index`(전체 인덱스 스캔) | 45·46ms |
| `LIKE '닥터수%'` (앞부분 일치) | 25,000건 — EXPLAIN `range` | 11·9ms |
| FULLTEXT 기본 파서 `'크림'` | **0건** — 2글자는 색인 단어가 아니다 | |
| FULLTEXT 기본 파서 `'선크림'` | 12,512건 — **띄어 쓴 단어만**, `어성초선크림`처럼 붙여 쓴 것은 못 찾는다 | |
| `WITH PARSER ngram` | **MariaDB: 테이블 생성 실패** `ER_FUNCTION_NOT_DEFINED` / MySQL: 생성됨 | |
| MySQL ngram `'크림'` (BOOLEAN) | 50,048건 — LIKE와 같지만 **더 느리다** | 77ms |
| MySQL ngram `'수분크림'` 자연어 모드 | **65,048건** — 정답은 1,252건 (2글자 조각 중 하나만 맞아도 나온다) | |
| MySQL ngram `'크'` (1글자) | 0건 | |
| 입력 `_` 또는 `%` 그대로 | **20만 건 전부** / 이스케이프하면 0건 | |
| NFD 입력 `'크림'`(5글자로 분리된 자모) | **0건** / NFC로 바꾸면 50,048건 | |
| `'spf50'` 소문자 | 39,936건 — `utf8mb4_unicode_ci`는 대소문자 무시 | |

### 3-3. 규모 — 언제 다른 수단을 검토하나 (MariaDB 11.4, 200만 행)

| 검색 | 20만 행 | 200만 행 |
|---|---|---|
| 흔한 단어 전체 COUNT | 43ms | 855~884ms |
| 흔한 단어 첫 페이지(LIMIT 20) | 3ms | 1ms — 앞에서 금방 20건을 채운다 |
| **드문 단어 첫 페이지**(LIMIT 20) | 81ms | **1,092ms** — 끝까지 훑는다 |
| 흔한 단어 상한 COUNT(1,001) | — | **6ms** |
| 드문 단어 상한 COUNT(1,001) | — | 895ms — 상한이 도움 안 된다 |
| 드문 단어 + 범위 조건(1/10로 좁힘) | — | **104ms** |

- 부분 일치 비용은 **훑는 행 수에 비례**한다. 범위 조건으로 훑는 행을 줄이는 것이 첫 처방이다.
- 범위 조건을 걸 수 없는 화면에서 대상 행이 수백만이고 드문 단어 응답이 1초를 넘으면(위 표) 검색 전용 저장소를 결정한다(⚑, 2절).

## 4. 함정 (STRICT)

| 함정 | 증상 | 처방 |
|---|---|---|
| **FULLTEXT 기본 파서로 한글 검색** | 2글자 단어("크림"·"세럼"·"토너")가 **0건**, 붙여 쓴 복합어 속 단어도 못 찾는다 (실측) | LIKE (3-1절) |
| MariaDB에서 ngram 파서 사용 | 테이블 생성 실패 — MySQL에서 만든 DDL이 MariaDB에서 깨진다 (실측) | 쓰지 않는다 |
| ngram 자연어 모드 | 정답 1,252건에 **65,048건** — 오탐 (실측) | 쓴다면 BOOLEAN 모드, 그래도 흔한 단어는 LIKE보다 느리다(실측) |
| 검색어를 이스케이프하지 않음 | `_`·`%` 한 글자로 **전체 행** — 검색이 전체 조회가 되고, 범위 조건이 없으면 무거운 쿼리를 누구나 만든다 (실측) | `toLikeTerm` |
| 백슬래시 이스케이프 + `NO_BACKSLASH_ESCAPES` | 정답 1건이 **0건** — 에러 없이 틀린다 (실측: 두 DB 모두. `ESCAPE '!'`은 두 모드 모두 1건) | `ESCAPE '!'` 명시 |
| NFD 입력·저장 | 같은 글자인데 0건 (실측) | 입력·저장 모두 NFC |
| 검색어를 SQL 문자열에 붙이기 | SQL 주입 | 바인딩 (sql.md 7절, 린트 규칙 — SQL에 요청 값 직접 보간 금지) |
| 매 검색마다 전체 COUNT | 200만 행에서 1초 가까이 — 목록보다 건수가 느리다 (실측) | 상한 COUNT |
| 범위 조건 없는 전체 기간 검색 기본값 | 드문 단어가 끝까지 훑는다 (실측 1,092ms) | 기간·상태 기본값 |

## 5. 스택별 구현

| 구성 | Express | Spring |
|---|---|---|
| 검색어 처리 | `toLikeTerm` (3-1절) | `Normalizer.normalize(s, Normalizer.Form.NFC)` + `replaceAll("[!%_]", "!$0")` + 길이 검사(`codePointCount`) |
| 쿼리 | mysql2 바인딩 `LIKE CONCAT('%', ?, '%') ESCAPE '!'` | JdbcClient·MyBatis `LIKE CONCAT('%', :term, '%') ESCAPE '!'` / JPA `cb.like(path, pattern, '!')` |
| 건수 | 상한 COUNT 서브쿼리 | 동일 |

## 6. 검증 포인트

- 자동화 테스트(테스트 DB): `_`·`%`·`!`가 든 이름을 정확히 찾는다 / 와일드카드만 입력하면 0건 / NFD 입력이 NFC 저장값을 찾는다 / 1자 입력 400 / 다른 법인 데이터가 섞이지 않는다.
- 운영 DB의 `sql_mode`를 확인해 CLAUDE.md에 기록 — `NO_BACKSLASH_ESCAPES` 유무와 무관하게 동작하는지 테스트 DB에서 같은 모드로 확인.
- 대상 테이블 행 수가 수백만에 가까워지면 3-3절 표를 운영 데이터 규모로 다시 재고 결정한다.
