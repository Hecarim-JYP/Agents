# 레시피: 탈퇴·파기·분리 보관 `[대외]` ⚑

> 확정: 2026-10-19 | 테이블: `schemas/20_retained_personal_data.sql`(별도 스키마) + `user.withdrawn_at` | 원칙: personal-data.md(접속기록·마스킹), sql.md 5절(소프트삭제) | 짝: social-login.md(연결 끊기), consent.md(동의 이력), session-control.md, batch.md(파기 배치)
> 탈퇴하면 user 행을 **지우지 않고 익명화**한다 — 주문·감사 로그의 참조는 남고 사람은 알아볼 수 없게. 다른 법령이 보존을 요구하는 값만 **별도 스키마로 옮겨 파기 예정일과 함께** 보관하고, 그날이 지나면 배치가 지운다.

## 1. 언제 쓰나

이용자가 스스로 가입하고 탈퇴하는 대외 서비스. 사내 시스템의 퇴사자는 인사 기록 보존 기준이 달라 이 레시피를 그대로 쓰지 않는다(계정 비활성 — auth.md 0절 프로비저닝).

### 1-1. 법정 요건 (확인 범위를 명시한다 — 2026-10-19)

| 항목 | 내용 | 확인 상태 |
|---|---|---|
| 파기 | 보유기간 경과·처리 목적 달성 등으로 불필요해지면 지체 없이 파기 (개인정보 보호법 제21조) | 조문 취지 — 검색 결과로 확인, 원문 미확인 |
| 분리 보관 | 다른 법령에 따라 보존해야 하면 파기하지 않고 **다른 개인정보와 분리**해 보관 (같은 조 / 표준 개인정보 보호지침 제11조) | 검색 결과로 확인, 원문 미확인 |
| "지체 없이"의 실무 기준 | **5일 이내**(교육부 지침 기반 공공 자료), 금융권 처리방침은 5영업일 | 2차 자료 — 법령 본문 기준 아님 |
| 장기 미이용자 분리(휴면) | **2023-09-15 시행 개정으로 의무 폐지**(개인정보 유효기간제) — 여러 서비스가 휴면 해제 공지 | 기업 공지로 교차 확인 |
| 전자상거래 거래기록 보존 (전자상거래법 시행령 제6조) | 계약·청약철회 기록 **5년**, 대금결제·재화 공급 기록 **5년**, 소비자 불만·분쟁처리 기록 **3년**, 표시·광고 기록 **6개월** | 5년·6개월은 2차 자료로 확인, **3년과 조문 원문은 미확인** |

- 위 기간·조문은 **프로젝트 시작 시 법무(또는 개인정보 보호책임자)가 원문으로 확인해 CLAUDE.md와 처리방침에 기록**한다 (MANDATORY) — 이 환경에서는 법령 정보 사이트에 접속하지 못했다.

## 2. 결정 항목 (기본값)

| 결정 | 기본값 | 대안 / 비고 |
|---|---|---|
| 탈퇴 시점 | **즉시** — 로그인 차단·세션 종료·익명화를 한 트랜잭션에서 | 철회 유예기간(예: 7일)을 두면 그동안 개인정보를 보관하는 것 — 처리방침에 기간 명시 |
| user 행 | **익명화**(행 유지) | 물리 삭제 — 주문·감사 로그·`created_by`의 논리 FK가 깨진다 |
| 법정 보존 값 | **별도 스키마 `{DB_NAME}_retention`로 이동** + `destroy_after` | 업무 테이블에 그대로 두고 접근만 막기 — "분리"로 보기 어렵다 |
| 재가입 제한 | **없음** — 익명화로 같은 이메일 재가입 가능 | 악용 방지로 제한하려면 이메일 해시를 기간 한정 보관 + 처리방침 명시 |
| 장기 미이용(휴면) | **하지 않음**(법적 의무 폐지) | 보안상 장기 미이용 계정 잠금은 서비스 정책으로 |
| 백업 | 백업 보관 주기만큼 남는다 — **복원하면 파기 목록을 다시 적용** | 처리방침에 백업 보관 기간 기재 |

## 3. 표준 설계

### 3-1. 탈퇴 트랜잭션

```
POST /api/me/withdraw { password 또는 재인증, reason? }
 BEGIN
  ① 법정 보존 대상 이동 — 같은 DB 서버의 별도 스키마라 한 트랜잭션에 묶인다
     INSERT INTO {DB_NAME}_retention.retained_personal_data (user_id, source_table, source_id, legal_basis, payload, destroy_after)
       SELECT user_id, 'orders', order_id, '전자상거래법 — 계약·청약철회 기록',
              JSON_OBJECT('recipient_name', recipient_name, 'recipient_phone', recipient_phone, 'address', address),
              DATE_ADD(ordered_at, INTERVAL 5 YEAR)
         FROM orders WHERE user_id = :userId
     UPDATE orders SET recipient_name = NULL, recipient_phone = NULL, address = NULL WHERE user_id = :userId
  ② user 익명화
     UPDATE user SET login_id = CONCAT('withdrawn:', user_id), user_name = '탈퇴회원', email = NULL,
                     password_hash = NULL, token_version = token_version + 1, is_active = 0, withdrawn_at = NOW()
      WHERE user_id = :userId AND withdrawn_at IS NULL                         ← 0행이면 이미 탈퇴 (중복 요청)
  ③ 부속 데이터 정리 (3-3절 표)
  ④ 외부 연결 끊기 요청 — outbox에 기록 (외부 쓰기 연동은 outbox 경유 — integration.md 4절)
 COMMIT → 세션 쿠키 삭제, 탈퇴 완료 메일(이메일을 지우기 전에 outbox로)
```

- 실측 2026-10-19 (MariaDB 10.11):
  - `is_active = 0`만 → 이름·이메일이 그대로 남고, **같은 이메일 재가입이 `ER_DUP_ENTRY`로 거부**된다.
  - 익명화 → 같은 이메일 재가입 성공, 기존 주문 조회는 `user_name = '탈퇴회원'`으로 그대로 동작.
  - ① 도중 실패 → 분리 보관 0건·주문 원상태(롤백) / 커밋 → 주문은 금액·일자만 남고 수령인은 분리 보관 1건(파기 예정 5년 뒤).
- 소셜 전용 사용자처럼 `password_hash`가 NULL 허용이 아니면(01_auth.sql 기본) `'!'` 같은 **해시가 될 수 없는 값**을 넣는다 — bcrypt·bcryptjs 모두 `compare`가 false를 돌려준다(실측, 예외 없음). `login_id`도 바뀌어 로그인 조회 자체가 되지 않는다.

### 3-2. 외부 연결 끊기

- 소셜 로그인 사용자는 제공사 **연결 끊기 API**를 호출하고 `user_identity`를 지운다 — 카카오는 회원 탈퇴 시 연결 끊기로 제3자 정보 제공 동의 철회까지 마무리하라고 안내한다(카카오 데브톡 운영 정책 안내).
- 반대 방향도 있다: 사용자가 제공사 쪽에서 연결을 끊으면 제공사가 알려주는 콜백(카카오 "연결 끊기" 설정)을 받아 같은 탈퇴 처리를 한다.
- 호출은 outbox relay가 한다 — 제공사 장애로 탈퇴가 실패하면 안 된다(outbox.md).

### 3-3. 무엇을 남기고 무엇을 지우나

| 데이터 | 처리 |
|---|---|
| `user` | 익명화 (3-1절 ②) |
| 주문·결제 등 거래 | 비식별 값(금액·일자·상품) 유지, 개인 식별 값은 분리 보관으로 이동 |
| `user_session`·`account_token`·`user_mfa*` | 삭제 |
| `user_identity` | 연결 끊기 후 삭제 |
| 프로필 사진 등 개인 업로드 | 파일과 `files` 메타 삭제 (거래 증빙 첨부는 거래 기록과 같이 보존) |
| `notification` | 삭제 |
| `login_history`·`audit_log`·`change_log` | 유지 — 행위자 참조(user_id)는 익명화된 행을 가리킨다. IP 등 보관 기간은 처리방침 기준으로 배치 파기 |
| 동의 이력 | consent.md 3-4절 |
| 개인정보 접속기록 | personal-data.md의 법정 보관 기간대로 유지 |

### 3-4. 분리 보관 조회·파기

- 분리 보관 스키마는 **앱 계정 INSERT만**, 조회는 권한 있는 담당자 화면에서 **사유 입력 + 접속기록**(personal-data.md 3절), 파기 배치 계정만 DELETE.
- 파기 배치(매일): `DELETE FROM retained_personal_data WHERE destroy_after < CURDATE()` — 실행 이력·실패 알림 필수(batch.md 3절), 삭제 건수를 이력에 남긴다(파기 증빙).

## 4. 함정 (STRICT)

| 함정 | 증상 | 처방 |
|---|---|---|
| 탈퇴 = `is_active = 0`만 | 개인정보가 무기한 남고, 같은 이메일 재가입 불가 (실측) | 익명화 |
| user 행 물리 삭제 | 주문·감사 로그 조인이 깨지고 행위자를 알 수 없다 | 익명화 |
| 보존 값을 업무 테이블에 그대로 | "분리 보관"이 아니고, 일반 화면에 계속 보인다 | 별도 스키마 이동 |
| 이동·익명화를 따로 커밋 | 중간 실패 시 값이 양쪽에서 사라지거나 양쪽에 남는다 | 한 트랜잭션 (실측) |
| 연결 끊기를 요청 안에서 동기 호출 | 제공사 장애로 탈퇴 실패 | outbox |
| 탈퇴 완료 메일을 익명화 뒤에 조립 | 보낼 주소가 이미 없다 | 익명화 전에 outbox 기록 |
| 백업 복원 후 파기 대상 부활 | 탈퇴자 정보가 다시 살아난다 | 복원 절차에 파기 목록 재적용 |
| 휴면 분리 보관을 "법적 의무"로 유지 | 불필요한 이중 저장·복잡도 (의무 폐지) | 서비스 정책으로만 |

## 6. 검증 포인트

- 자동화 테스트(테스트 DB): 탈퇴 후 로그인 불가 / 같은 이메일 재가입 성공 / 기존 주문 조회 정상 / 분리 보관 행의 `destroy_after` / 탈퇴 도중 실패 시 롤백 / 같은 요청 두 번 → 두 번째는 409.
- 파기 배치: `destroy_after`가 지난 행만 삭제되고 실행 이력에 건수가 남는지.
- 처리방침과 일치 확인: 보존 항목·기간·근거가 1-1절(법무 확인본)과 같은지.
