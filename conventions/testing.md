# 자동화 테스트 컨벤션

무엇을·어떻게 테스트하고, 테스트 없는 변경을 어떻게 다루는지 정의한다. (2026-07-11 확정 — 근거: 정적 추적/수동 스모크만으로는 회귀 안전망이 없어 "코드완료·런타임 검증 필요" 상태가 누적되는 문제)

## 0. 테스트 DB 사용 여부 — 프로젝트 시작 시 결정 (스캐폴드 체크리스트)

서비스·리포지토리를 어떻게 테스트할지는 **테스트 전용 DB를 두는가**에 따라 갈린다. 시작 시 확정해 CLAUDE.md에 기록한다.

| | (a) 테스트 DB 사용 (권장) | (b) 테스트 DB 없음 |
|---|---|---|
| 서비스 테스트 | **실제 테스트 DB에 연결해 검증** — 쿼리·트랜잭션·제약까지 함께 검증된다 | 쿼리 계층을 **목킹**(Vitest `vi.mock` / Spring `@MockBean`)하고 서비스 로직만 검증 |
| 쿼리 테스트 | 가능 — 동시성(낙관적 락·조건부 UPDATE, sql.md 8절)과 UNIQUE 제약은 **실제 DB에서만 검증된다** | 불가 — 이 영역은 테스트로 못 잡는다는 한계를 CLAUDE.md에 명시 |
| 구성 | dev override의 `db-test` 서비스(스캐폴드 템플릿에 포함 — 데이터는 tmpfs라 기동 시 초기화) + `.env`의 `TEST_DB_*`. 각 테스트는 트랜잭션 롤백 또는 데이터 초기화로 **서로 독립**하게 (2절) | 추가 구성 없음 |

- (a)를 선택하면 **CI에도 테스트 DB를 띄운다** — GitHub Actions job의 `services:` 블록(스캐폴드 test.yml 템플릿에 포함). 이걸 빠뜨리면 로컬은 통과하고 CI만 깨진다.
- **운영 DB는 어떤 테스트·검증에도 사용하지 않는다 (STRICT).** **자동화 테스트(`npm test`·CI·stop-test 훅)는 테스트 DB 전용**이다 — 데이터 초기화를 하므로 개발 DB에 붙이면 공유 데이터가 지워지고, 기존 데이터가 섞여 결과가 비결정적이 된다(로컬은 개발 데이터, CI는 빈 DB라 결과도 갈린다). stop-test 훅은 코드를 고친 턴마다 자동 실행되므로 사용자가 모르는 사이에 반복된다. 개발 DB에서의 **수동 실동작 검증**은 6절을 따른다 (2026-10-14 분리 — 이전 문구 "운영·개발 DB 금지"는 수동 검증까지 막았다).
- 어느 쪽이든 **인터페이스 추상화(리포지토리 인터페이스 + 구현체 주입)를 위해 계층을 늘리지 않는다** — 테스트 가능성은 실제 DB 또는 모듈 목킹으로 확보하고, 코드 구조는 단순하게 유지한다 (patterns.md 6절 성급한 추상화 방지).

## 1. 무엇을 테스트하나 (우선순위)

1. **서비스 계층 비즈니스 로직 단위 테스트** — 계산, 검증, 분기, 상태 전이. 0절의 결정에 따라 테스트 DB 연결 또는 쿼리 목킹으로 수행한다(순수 계산은 도메인 함수로 분리해 DB 없이 검증 — patterns.md 2절).
2. **API 계약 통합 테스트** — 엔드포인트별 응답 상태코드·응답 키 구조·에러 본문 계약(patterns.md 3절). 계약이 코드로 고정되면 응답 형식 회귀를 자동으로 잡는다.
3. **버그 재발 방지 테스트** — 버그를 수정할 때는 가능하면 **재현 테스트를 먼저** 쓰고 수정한다. 백로그 완료 항목의 "재현 안 됨" 근거가 된다.

## 2. 무엇을 하지 않나

- **커버리지 % 목표 금지** — 수치를 채우기 위한 무의미한 테스트가 양산된다. 위 우선순위 대상만 채운다.
- 단순 매핑/getter/상수 테스트, UI 스냅샷 남발 금지.
- 실행 순서에 의존하는 테스트 금지 — 각 테스트는 독립적으로 통과해야 한다 (general.md 7절).

## 3. 프레임워크 표준

| 스택 | 도구 |
|---|---|
| TypeScript/JavaScript (클라·서버 공통) | **Vitest** (Vite 생태계, 설정 최소) |
| API 통합 테스트 (TS) | Vitest + **supertest** (서버 기동 없이 앱 객체 직접 호출) |
| **Java/Spring** | **JUnit 5** — API 계약은 `@WebMvcTest`/`MockMvc`, 서비스 도메인 로직은 컨텍스트 없는 순수 단위 테스트. 실행은 `./gradlew test` (spring.md 7절). 메서드명은 4절의 Java 예외 참조 |
| React 컴포넌트 | Testing Library — 핵심 인터랙션(권한 게이트, 폼 검증)만 |
| Python | **pytest** |

## 4. 구조와 네이밍

- 위치는 프로젝트 초기에 결정해 CLAUDE.md에 기록: `tests/` 미러링 또는 소스 인접 `*.test.*` 중 하나로 통일.
- 테스트 이름은 검증하는 행동을 서술한다: `만료된_세션은_거부된다`, `생성_성공시_201과_data_키를_반환한다`.
  - ⚠ **Java는 예외 (2026-07-14 실측)**: Checkstyle의 `MethodName` 규칙이 camelCase를 강제하므로 **메서드명은 camelCase로 두고 서술은 `@DisplayName`에 적는다** (`@DisplayName("생성_성공시_201과_data_키를_반환한다") void createReturns201WithData()`). 스네이크 메서드명을 쓰면 `./gradlew check`가 실패한다 — 규칙끼리 부딪히므로 도구 쪽을 따른다.
- 실행 명령은 항상 `npm test`(또는 `pytest`)로 통일 — 스크립트 별칭을 두어 CI와 로컬이 같은 명령을 쓴다.

## 5. 게이트 규칙 (STRICT — 게이트+기록 방식)

- **핵심 로직(서비스 계층·계산·검증·상태 전이·권한 판정) 변경 시 테스트 동반 작성이 원칙.**
- 사정상 못 썼으면 숨기지 말고 기록한다:
  1. 완료 보고에 **"테스트 미작성"** 명시
  2. changelog(dev_log)에 미작성 사실과 사유 명시
  3. 백로그에 `TEST-` ID로 항목 추가 (심각도·근거 포함)
- 검증 단계에서 `npm test`를 실행하고 결과를 보고한다. **실패 테스트를 숨기거나 skip 처리로 얼버무리는 것 금지** — 실패는 실패라고 보고.
- 문서·설정만 바꾼 변경은 게이트 대상이 아니다.

## 6. 실동작 검증 — 개발 환경에서 실제로 돌려 확인 (2026-10-14 확정)

자동화 테스트(1~5절)와 정적 추적(/paper-test)이 못 보는 영역 — **런타임 동작·실제 DB 데이터·외부 시스템 실응답·동시성·브라우저 렌더링** — 을 개발 환경에서 실제로 돌려 확인하는 수동·탐색 검증의 규칙이다. 절차는 `~/.claude/skills/live-test/SKILL.md`가 단일 출처다. (근거: 정적 추적의 "② 의심" 항목과 "코드완료·런타임 검증 필요" 상태가 실측으로 확정되지 못한 채 누적되는 문제)

### 6-1. 대상 환경 — 운영 DB에는 접속하지 않는다 (STRICT)

- **운영 DB에는 조회를 포함해 어떤 작업도 하지 않는다.** 판별 기준은 프로젝트 CLAUDE.md "프로젝트 참고사항"의 **운영 DB 식별자**(호스트·포트·DB명 — 시작 결정 체크리스트 25)다. 검증 시작 전 현재 접속 설정(`.env`·`application.yml`·`web.config`·`config.php` 등 스택의 설정 파일)을 읽어 대조한다. Claude의 직접 조회뿐 아니라 **검증 대상 앱의 접속 설정도 대조 대상**이다 — 앱이 운영 DB를 가리키면 화면 조작 자체가 운영 쓰기이므로 검증 전체를 중단한다.
- **식별자가 기록돼 있지 않거나 대조 결과가 모호하면 진행하지 않고 묻는다** (fail-closed). 답을 받으면 CLAUDE.md에 기록한다 — 판별 기준이 대화가 아니라 문서에 남아야 다음 검증도 같은 기준으로 막힌다.
- 근거: 개발 DB에서는 쓰기를 허용하므로(6-2절) 운영을 개발로 오판하는 한 번이 곧 운영 데이터 오염이다. 포트·폴더를 아무리 나눠도 접속값 하나로 뚫린다 (docker.md 7-2절의 볼륨 공유 사고와 같은 유형).
- 권장 — 도구로 강제: 실동작 검증에 쓰는 개발 DB 계정에는 `SELECT, INSERT, UPDATE`만 부여하고, 운영 접속 정보는 개발 PC의 설정 파일에 두지 않는다. 문서 규칙이 아니라 DB 권한이 막게 한다.

### 6-2. 개발 DB 허용 범위와 테스트 데이터 (STRICT)

| 허용 | 금지 |
|---|---|
| 조회·삽입·수정 (`SELECT`·`INSERT`·`UPDATE`) | 삭제(`DELETE`)·DDL(`DROP`·`TRUNCATE`·`ALTER`·`CREATE`) |

- 테스트가 만든 레코드는 **테이블·PK를 작업 폴더(6-4절)에 기록**한다 — 정리와 보고의 근거다. 사람이 화면에서 알아볼 수 있게 문자열 컬럼에는 `__LT_` 접두어를 붙인다(형식 검증 때문에 못 붙이는 컬럼은 PK 기록으로 충분하다).
- 행을 잠그거나 반복 수정하는 검증(동시성 등)은 **테스트가 만든 레코드만** 대상으로 한다 — 공유 개발 DB에서 다른 사람의 작업 데이터를 잠그거나 덮어쓰지 않기 위함이다.
- 정리는 **소프트삭제(sql.md 5절 — UPDATE)**로 한다. 앱이 검증 중 만든 **미발송 연동 대기 행**(outbox 등)은 종결 상태로 UPDATE한다 — 남겨두면 나중에 발송된다. 소프트삭제 컬럼이 없는 테이블에 남은 행은 지우지 않고 **잔존 목록(테이블·PK)으로 보고**한다.

### 6-3. 외부 연동

- 외부 시스템 호출은 제한하지 않는다 (2026-10-14 확정 — 쓰기 연동은 연동 대기 행(outbox)을 경유하고, 쓰기가 필요한 연동은 상대 시스템의 테스트 환경을 지정해 개발한다는 전제).
- 검증 스크립트가 직접 보내는 쓰기 호출은 재시도하지 않는다 (integration.md 4절 — 응답 유실 시 중복 처리).
- 검증 시작 시 **연동 대상 URL을 환경 요약에 표기**한다 — 차단이 아니라, 결과를 읽는 사람이 어느 상대에 붙은 결과인지 알게 하기 위함이다.

### 6-4. 작업 폴더·증거

- 일회성 스크립트·스크린샷·응답 로그는 **대상 프로젝트 밖** `{os.tmpdir()}/jyp-live-test/{프로젝트명}/{YYYY-MM-DD}/`에 둔다 — 어느 저장소에도 올라가지 않는다. 스크립트 의존성(Playwright 등)도 이 폴더에 설치하고, 대상 프로젝트 `package.json`에 추가하지 않는다.
  - 근거: 프로젝트 안에 두면 post-edit 훅이 상위 `package.json`을 찾아 프로젝트 전체 lint·typecheck를 돌리고 테스트 마커를 남겨, stop-test 훅의 `npm test`가 그 스크립트까지 실행할 수 있다. 훅은 git이 아니라 작업 트리 기준이라 `.gitignore`로 막히지 않는다 (qa-claude의 "재현 테스트 파일 금지"와 같은 이유).
  - `~/.claude/jyp/` 아래는 금지 — install이 매번 비우고 새로 복사한다.
- 판정은 **실측 증거로만** 한다 — HTTP 요청/응답 요약, SQL 조회 결과, 로그 라인, 스크린샷 경로. "저장됐을 것" 같은 추측 판정 금지.
- 보고는 텍스트 증거로 자기완결되게 쓴다(스크린샷은 작업 폴더에만). 보고·증거에 남는 **개인정보·접속 정보·키·테스트 계정 비밀번호는 마스킹**한다.

### 6-5. 자동화 테스트와의 경계

- 0절의 "자동화 테스트는 테스트 DB 전용"은 그대로다 — 이 절은 수동 검증에만 적용된다.
- 반복 가치가 있는 시나리오는 **사용자 승인 시에만** 대상 프로젝트의 자동화 테스트로 승격한다(1~5절 적용). 브라우저 E2E는 `npm test`와 분리된 별도 스크립트(`test:e2e`)로 둔다 — stop-test 훅이 매 턴 실행하는 `npm test`에 브라우저 테스트를 넣으면 턴마다 앱 기동과 브라우저 실행을 요구한다.
