# 통합 테스트 (정적 추적 + 실측)

통합 테스트의 상위 명령이다. **1단계 정적 추적**(/paper-test 절차)으로 코드를 읽어 넓게 훑고, **2단계 실측**으로 개발 환경에서 실제로 돌려 확정하고, **3단계**에서 항목마다 두 판정을 합친다. 정적 추적만 따로 돌리고 싶으면 /paper-test를 단독으로 쓴다.

실측 단계의 규칙(대상 환경·개발 DB 허용 범위·테스트 데이터·외부 연동·작업 폴더·증거)의 단일 출처는 `~/.claude/jyp/conventions/testing.md` 6절, 정적 단계의 절차는 `~/.claude/skills/paper-test/SKILL.md`다 — 이 문서는 둘을 잇는 절차만 담는다.

## 구조

| 단계 | 하는 일 | 근거 형태 | 병렬 에이전트 |
|---|---|---|---|
| 0. 환경 판별 | 실측 가능 여부로 **모드** 결정 + (전체 모드면) 운영 DB 대조 | — | — |
| 1. 정적 추적 | /paper-test 절차 — 인벤토리 → 계약 체크리스트 → 읽기 전용 추적 | `파일:라인` + 스니펫 | 허용 (읽기 전용) |
| 2. 실측 | 1단계 결과 + 정적으로는 못 보는 5개 축을 실제로 돌려 확인 | 실측 증거 (testing.md 6-4절) | **금지** |
| 3. 통합 판정 | 항목마다 정적 판정 × 실측 판정 → 최종 3분류, 백로그 반영 | 둘 다 | — |

## 실측 방법론 — 하이브리드

| 모드 | 화면 조작 | Claude의 역할 | 쓰는 곳 |
|---|---|---|---|
| 자동 조작 | Claude (브라우저 도구 또는 작업 폴더의 Playwright 스크립트) | 시나리오 실행·스크린샷·판정 | 데이터 준비, 스모크·회귀 확인, 동시성 |
| 관찰자 | **사용자** | 단계별 스크립트(조작 + 기대 결과)를 주고, 각 단계 직후 DB 행·서버 로그·API 응답을 조회해 판정 | 인수 확인, UX 판단, SSO·MFA가 걸린 화면(사용자가 로그인한 세션을 이어받는다) |

- 기본은 둘을 섞는다 — 사람의 눈이 필요한 화면은 관찰자, 나머지는 자동 조작. 시나리오마다 모드를 표기한다.
- 판정은 실측 증거로만 한다 (testing.md 6-4절). 화면에 "저장됨"이 떴어도 DB를 조회해 확인한다.

## 절차

### 0. 환경 판별 (생략 금지)

- **모드 결정** — 앱을 기동할 수 있고 개발 DB에 접속할 수 있으면 **전체 모드**(1→2→3), 아니면 **정적 모드**(1→3, 실측 축은 모두 "–"와 이유). 클라우드 세션처럼 사내망 밖이면 정적 모드다.
- **전체 모드면 운영 DB 대조** — testing.md 6-1절대로 현재 접속 설정을 프로젝트 CLAUDE.md의 운영 DB 식별자와 대조한다. 운영과 일치하면 **2단계 전체를 중단**하고 정적 모드로 전환한다(앱이 운영 DB에 붙어 있으면 화면 조작 자체가 운영 쓰기다). 식별자가 없거나 모호하면 묻고 CLAUDE.md에 기록한 뒤 진행한다.
- 결과를 **환경 요약**(모드·앱 URL·DB 호스트/DB명·연동 대상 URL·작업 폴더)으로 먼저 보고한다.

### 1. 정적 추적

- `~/.claude/skills/paper-test/SKILL.md`를 읽고 **그 절차 1~4단계를 그대로 수행**한다 — 인벤토리 확인 → 계약 체크리스트 → 읽기 전용 에이전트 추적 → 라운드 분할. 절차를 여기에 다시 쓰지 않는다.
- paper-test의 **5단계(백로그 반영)는 여기서 하지 않는다** — ② 의심이 실측으로 ③ 정상이 되면 백로그에 넣을 필요가 없으므로, 3단계에서 최종 판정 후 한 번에 반영한다.
- 산출물: 인벤토리, 항목별 정적 판정(①②③)과 `파일:라인` 근거.

### 2. 실측 (전체 모드만)

1. **대상 선정** — 1단계 결과에서 고른다:
   - **② 의심 전부** — 실측으로 ① 또는 ③으로 확정한다
   - **① 확인된 버그** — 재현해서 백로그에 넣을 재현 절차와 증거를 만든다
   - **③ 정상 중 핵심 플로우 표본** — 인벤토리에서 사용자와 정한다
   - **정적으로는 못 보는 5개 축 시나리오** — 런타임·실DB·외부 연동·동시성·렌더링

   시나리오마다 입력값·권한(테스트 계정)·사전 상태·기대 결과·검증 축·모드를 명시한다. 권한별 테스트 계정이 필요하면 사용자에게 받는다.
2. **기동 확인** — 앱 기동은 프로젝트 CLAUDE.md의 방법(없으면 /run)을 따른다. `/health`·첫 화면 응답·서버 로그 위치를 확인한다. 기동이 안 되면 그 자체를 ① 확인된 버그로 기록하고 정적 모드로 전환한다.
3. **실행** — 시나리오별로 수행하며, 생성한 레코드의 테이블·PK를 작업 폴더에 기록한다. 축별 확인 방법:
   - 런타임: API 상태코드·응답 봉투(api.md 5절), 서버 로그의 에러·경고
   - DB: 조작 직후 대상 행 조회 — 값, 공통 컬럼(작성자·일시), `version` 증가, 감사 로그 기록
   - 외부 연동: 실제 응답과 매핑 결과, 쓰기 연동이면 연동 대기 행(outbox)의 생성·상태 전이 (`~/.claude/jyp/conventions/features/outbox.md` 6절)
   - 동시성: 테스트가 만든 레코드에 병렬 요청 또는 두 브라우저 컨텍스트로 동시 수정 → 한쪽 409 + 데이터 무결 (sql.md 8절). 비결정적이므로 **N회 반복한 결과**로 판정한다
   - 렌더링: 스크린샷, 콘솔 에러, 실패한 네트워크 요청, 로딩·빈 상태·에러 3종(design.md 5절)
4. **라운드 분할** — 범위가 크면 라운드로 나눠 결과를 보고한 뒤 다음을 진행한다. 1단계와 달리 **병렬 에이전트로 동시에 돌리지 않는다** — 같은 DB·브라우저 상태를 공유해 서로의 결과를 오염시킨다.
5. **정리** — testing.md 6-2절대로 테스트 데이터를 소프트삭제하고, 미발송 연동 대기 행을 종결 상태로 바꾸고, 남은 행은 잔존 목록으로 보고한다.

### 3. 통합 판정·백로그

항목마다 두 판정을 합쳐 최종 3분류를 정한다:

| 정적 판정 | 실측 판정 | 최종 | 의미 |
|---|---|---|---|
| ① 버그 | 재현됨 | **①** | 확정 — 재현 절차와 증거 첨부 |
| ① 버그 | 재현 안 됨 | **②** | 정적 근거 재검토 필요 (조건 미충족 또는 오탐) |
| ② 의심 | 결함 확인 | **①** | 의심 확정 |
| ② 의심 | 정상 확인 | **③** | 의심 해소 |
| ③ 정상 | 결함 확인 | **① ★정적 누락** | 코드만 읽어서는 못 잡은 유형 — **별도 목록으로 표시** |
| ③ 정상 | 정상 확인 | **③** | 확정 정상 |
| 무엇이든 | – (실측 안 함) | 정적 판정 그대로 | "실측 미수행"과 이유 표시 |

- 동시성 항목이 N회 반복에서 재현되지 않았으면 ③으로 두되 "N회 미재현"을 함께 적는다 (안전하다는 증명이 아니다).
- **백로그 반영** — 최종 ①과 남은 ②를 성격에 맞는 ID(`SEC/BE/FE/DB/OPS/DEAD`)로 `docs/REFACTORING_BACKLOG.md`에 추가한다(templates/backlog.md 필수 필드). 근거 = 정적 근거(`파일:라인`) + 실측 증거 요약 + 재현 절차. ★정적 누락은 근거에 그 표시를 남긴다 — 같은 유형을 다음 정적 추적의 계약 체크리스트에 넣을 후보다.
- ⚠ **코드 수정 금지** — 발견만 보고하고, 수정은 사용자 승인 후 별도로 한다.

## 출력 형식

- 맨 앞: 환경 요약 (0단계 — 모드 포함. 정적 모드면 "실측 미수행 — 이유"를 첫 줄에)
- 1단계 요약: 인벤토리, 정적 판정 집계
- 2단계 시나리오별: `시나리오(모드) → 조작 → 실측 증거 → 판정 ✅/⚠️/❌`
- **통합 판정표**: `항목 | 정적 판정(파일:라인) | 실측 판정(증거) | 최종`
- **★정적 누락 목록** (있을 때)
- 발견 항목: 심각도(High/Med/Low) + 근거 + 재현 절차 + 수정 제안
- 마지막에 **① 확인된 버그 ② 의심(추가 확인 필요) ③ 정상 확인** 최종 3분류 요약 + 정리 결과(소프트삭제 건수·잔존 목록)

## 범위 한계 (반드시 고지)

- 정적 모드로 끝났으면 ② 의심이 확정되지 않은 상태다 — 실측 가능한 환경(회사 PC 등)에서 다시 실행을 제안한다.
- 실측은 개발 환경 기준이다 — 운영 데이터의 분포·예외 케이스·규모와 운영 인프라(프록시·네트워크) 차이는 검증하지 못한다.
- 동시성은 N회 반복에서 재현되지 않았다는 것이지 안전하다는 증명이 아니다. 부하·성능 테스트가 아니다.
- 렌더링은 실행한 브라우저 엔진에서만 확인된다.
- 사내망 DB·API는 사내망에 붙은 세션(회사 PC 로컬)에서만 닿는다 — 접근할 수 없는 축은 "–"로 표기하고 이유를 적는다.
